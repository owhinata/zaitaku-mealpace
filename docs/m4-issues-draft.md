### M4-1 UNO Q の Linux 側で推論を動かす土台と、1 窓あたりの処理時間の計測

ラベル: firmware、analysis　Milestone: M4

**背景**

M4 は装置（UNO Q）の上で推論する（docs/plan.md、0025）。#38 で LED の RPC・PD 電源・arduino-cli と、Linux 側のコードの置き場所（`device/unoq/`、rsync で配る。0035）が整った。
UNO Q には numpy・pip が無く（0028）、M3 の推論（0034 の構成 J: `mfe40` の特徴量＋numpy の CNN 順伝播。構成 R: `a52`＋ロジスティック回帰）は PC では 1 窓 1.05 ms だが UNO Q では未計測（0034「確かめていないこと」）。
人の意向（10/11）: 1 ホップ 0.25 → 0.1 秒の判断の材料に、1 窓の処理時間（特徴量・推論・RPC）の実測が要る。

**やること**

- UNO Q に `python3-numpy`（Debian 13 のパッケージ）を人が入れる（sudo）。版を 0035 の追記に固定する。librosa・scipy は入れない（D3）。
- `analysis/features_v2.py` の `mfe40`（フレーム 400/160、Hamming、プリエンファシス 0.97、`n_fft` 512、メル 40 本 0〜4000 Hz、対数）を **numpy だけ**で計算する関数を分け、メルのフィルタ行列は PC で `librosa.filters.mel` から作った `.npy` を定数として読む。
  PC で librosa 版と numpy 版が同じ値（float32 で 1e-5）を出すことをテスト。`a52` の `delta` も同様（必要なら）。
- `device/unoq/DEPLOY_FILES` に、推論に要る共有ファイル（numpy 版の特徴量、`postprocess.py`、CNN の順伝播 `cnn_forward`、メル行列 `.npy`、CNN の重み `.npz`（学習の成果。音声ではない））を足す。
  `analysis/` のファイルを配る形（0035「M4 は同じ一覧に PC と同じ推論のファイルを足す」）。`__pycache__` は作らない（`python3 -B`）。
- 計測スクリプト `device/unoq/bench_infer.py`（合成入力。乱数と正弦波。音声は使わない。ファイルを書かない）: 1 窓（16000 サンプル）の特徴量、CNN の順伝播、`a52`＋LR、`zm_set_state` の往復を各 200 回、中央値と 95 パーセンタイルと最大。1 スレッドと既定のスレッド数。
- 0.1 秒のホップで必要になる「0.1 秒ごとに 1 窓」の処理が収まるか（1 窓の合計 < 100 ms か）を数字で書く。判断は別の decision（D5）。
- 結果を docs/log と 0035 の追記に書く。

**完了の条件**

- UNO Q で numpy 版の特徴量と CNN の順伝播が動き、PC の librosa 版と同じ値を出す（テスト）。
- 1 窓の処理時間（特徴量、CNN、LR、RPC）の中央値・95 パーセンタイルが log にある。1 ホップ 0.25 秒に収まるか、0.1 秒に収まるかの事実が書いてある。
- UNO Q に音声のファイルが無い（docs/unoq-setup.md の確かめ方）。

**関係するファイル**: `analysis/features_v2.py`、`device/unoq/`（`DEPLOY_FILES`、`bench_infer.py`）、docs/decisions/0035（追記）、docs/unoq-setup.md、docs/log/

**制約**: 推論のパイプラインに触れるので Codex の plan レビューの対象。装置側は生の音声を保存も送信もしない（この Issue では音声を扱わない）。UNO Q に置くのは `DEPLOY_FILES` の一覧だけ。

### M4-2 誤検出を減らす検討（学習側だけ。M4 の合格線 1 回/分に向けて）

ラベル: analysis　Milestone: M4

**背景**

M3 の評価側で、判定に使った構成 J（CNN `mfe40` 種 0、ヒステリシス 0.95/0.85）は検出 30/30、誤検出 1.19 回/分（docs/log/2026-10-13.md）。M4 の合格線は 85% / **1 回/分以下**で、このままでは届かない（人の考え、#41）。
M3 の誤検出 23 回の内訳は water の非嚥下区間 9、saliva 5、neck 5、talk 4、cough 0、quiet 0。嚥下の直後に陽性が `[t − 0.5, t + 1.5]` を越えて続くと誤検出に数えられる。
学習側は 1 収集日 14 本だけだった。

**やること**

- M4-3 の分割（学習側 = M3 の 21 本＋追加の条件別＋学習用 `meal`）で、学習側だけを使う。評価側（`meal` の最後の 2 収集日）は名前以外読まない。
- 誤検出の中身の分析（学習側 CV の検証側の確率で）: 嚥下の直後の延び（塊が `t + 1.5` を越える）、動作に付くもの（talk・neck・cough）、`meal` の中の咀嚼・会話、に分けて数える。図は #43 の `visualize.py` を使う。
- 候補（すべて学習側 CV で比べ、評価側で選ばない）:
  1. ヒステリシスの出を上げる（格子は 0033 の 45 点のまま）。
  2. 陽性の塊の長さの上限（例: 2.0 秒を越えた分は陰性に）。
  3. 検出の直後の不応期（塊の終わりから N 秒は新しい塊を作らない。N は {0.5, 1.0, 1.5}）。
  4. CNN の 3 種（0・1・2）の確率の平均（アンサンブル）。
  5. 学習データの増強（M4-3 の追加分）。
  - 採らないもの: 多数決（人の決定 10/4）、評価の定義の変更（窓・数え方・合格線）、ホップの変更（D5）。
- 組の選び方: 0014 の規則を「誤検出 1.0 回/分以下のうち検出率が最大、同率なら単純なほう。満たす行が無ければ誤検出が最小」に読み替える。
- 選んだ構成（特徴量・分類器・種・後処理の値）を **docs/decisions/0038 に事前に固定**し、評価側を開く前にコミットする（0033・0034 と同じ）。
- `docs/evaluation.md` 28 行目の手法（M2 の行は Edge Impulse）からの逸脱は 0034 と同じく記録する。

**完了の条件**

- 学習側 CV の表（候補ごとの検出率・誤検出率・陽性窓の割合）と図が log にあり、選んだ構成が 0038 に固定されている。
- 評価側（`meal`）を 1 本も開いていない（`fixed_eval.py` の検査が通る）。
- 合成データのテストが通る（新しい後処理の入り・出・不応期・塊の上限）。

**関係するファイル**: `analysis/postprocess.py`、`analysis/compare.py`、`analysis/visualize.py`、`analysis/fixed_eval.py`、docs/decisions/0038（新規）、docs/log/

**制約**: 評価の分割と指標、推論のパイプラインに触れるので Codex の plan レビューの対象。評価側を見てから組・閾値・後処理を変えない。`docs/evaluation.md` は変えない。

### M4-4 装置上の推論と表示（UNO Q の Linux 側 `detector.py`、MCU のマトリクス、PC の受け口）

ラベル: firmware、analysis　Milestone: M4

**背景**

M4 の中心。UNO Q の Linux 側が ALSA から音をメモリに取り、特徴量に変換して破棄し、推論と後処理と 0018 の規則で状態を決め、MCU に RPC で送る（0025、CLAUDE.md「データの扱い」「実装方針」）。

**やること**
