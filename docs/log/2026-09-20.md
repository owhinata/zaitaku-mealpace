## 分かったこと

- Target device の一覧に Arduino Nano RP2040 Connect が無かった。同じ MCU の「Raspberry Pi RP2040」を選び、
  RAM と ROM を Nano RP2040 Connect の値（264 KB、16 MB）にした。Studio の性能見積もりはこの設定が基準になる。
  実機での推論時間と RAM は M2 で実測する。
- Latency の目標を 100 ms にした理由: `docs/evaluation.md` のホップは 0.25 秒なので、装置上では 250 ms ごとに
  DSP と推論を1回終える必要がある。Cortex-M0+ は FPU が無く MFCC が重い見込み（推測）なので、推論を 100 ms に
  抑えて DSP とセンサの読み出しに 150 ms を残す。この値は EON Tuner の探索の上限と見積もりの基準に使われるだけで、
  後から変えられる。
- Edge Impulse の標準のセンサフュージョンは、全チャンネルが同じサンプリング周波数であることが前提。
  16 kHz の音声と 104 Hz の IMU は、そのまま1つの時系列としては投入できない。企画書の
  「IMU と音を結合して1つの分類器に入れる」をどう実現するかは M2 で決める必要がある。案は3つ。
  PC 側で窓ごとの特徴量を計算して特徴量として投入する。音声だけを学習して IMU は装置側の簡単なルールで併用する。
  カスタム処理ブロックを書く。1つ目は `analysis/features.py`（#11）の作り方に関わる。

## #11 窓ごとの特徴量

`analysis/features.py` を合成セッション（`tempfile` に作る。実データは使わない）で確かめた。式は docs/decisions/0012。

| 確かめたこと | 結果 |
|---|---|
| 10.000 秒のセッション | 37 窓 × 29 次元。`t_ms` が 123456 から始まっても 37 窓 |
| 60 秒のセッション | 237 窓。`extract_session` は約 0.16 秒 |
| 1 kHz の正弦波 | スペクトル重心 999.93 Hz、ゼロ交差率 0.1249 |
| Y 軸に 5 Hz・振幅 0.1 g の正弦波 | 主軸 `[0, 1, 0]`、Y の RMS 0.0706〜0.0709、peak-to-peak 0.1997〜0.2、ピーク数 9〜10 |
| ジャイロに +1 dps のオフセット | ジャイロの RMS と peak-to-peak は変わらない（窓内の平均を引いている） |
| IMU を 30 行抜く / 音声チャンクを 25 個抜く | 飛びと交わる 5 窓だけ `valid = False`。グリッドは等間隔のまま。以降の窓の音声は正しい時刻から取られる |

- 「同じ分散で無相関なら主軸は既定値」のテストは、plan の `A sin` / `A cos`（IMU 周期 9.48 ms）だと離散化のせいで
  `(λ1 − λ2) / λ1` が 0.0080〜0.0111 になり、閾値 0.01 の境目に来た。式と閾値は変えず、テストの入力を IMU 周期 10 ms
  ちょうど（各窓が 5 Hz の整数周期）に替えた。比は 0.0 で全窓が既定値。境目の反対側（Y の振幅を 0.8 倍、比 0.360）では
  固有ベクトル `[1, 0, 0]` が返る。
- `data/sample/` の見本（#9、`self` / `quiet` の 10 秒）では 36 窓 × 29 次元、`valid` 36/36。

## #15 音声チャンクの `t_ms`

文書を実装に合わせた（docs/decisions/0013）。ファームウェアは変えていない。`docs/data-schema.md` の一文を直し、
`analysis/features.py` は先頭サンプルの時刻を `t_ms − 1000 × チャンクのサンプル数 ÷ audio_hz` ms で求める。音声の飛びの判定も
換算後の時刻（前のチャンクの終端と次のチャンクの先頭の間の空白）から出す。テストは 81 件。見本は 36 窓 × 29 次元のまま。

叩きの実測（基板を机に置いて60秒、ペンで軽く叩く。抽出の規則は記録を見る前に固定。規則は 0013）:

| 項目 | 値 |
|---|---|
| 記録 | 60.014 秒、IMU 6333 行、音声 15005 チャンク、`t_ms` の飛び 0 箇所 |
| IMU の候補 / 対にできた数 / 除外 | 50 / 50 / 0 |
| Δ = 音 − IMU、`t_ms` を先頭サンプルの時刻とみなした場合 | 中央値 −3.9 ms、四分位範囲 −6.0〜−1.8 ms、最小 −99.9、最大 +0.9 |
| Δ = 音 − IMU、`t_ms` を終端側の時刻とみなした場合（採用） | 中央値 −7.9 ms、四分位範囲 −10.0〜−5.8 ms、最小 −103.9、最大 −3.1 |

- どちらの読み方でも、ずれは ±10 ms 程度に収まっている。IMU は約 9.5 ms 周期で、立ち上がりは次に読まれた行にしか現れない
  （平均 約 +4.7 ms）。4 ms の差をこの実測で切り分ける分解能は無い。終端側の時刻と読む根拠は、コード（`PDM.read()` の後に
  `millis()`）とボードコアの実装に置いた。
- 50 対のうち 2 対が外れた（−24.9 ms、−99.9 ms）。−99.9 ms は音を探す範囲の左端で、叩きより前の音が閾値を超えたものと
  見られる（未確認）。規則どおり除外せず、中央値と四分位範囲で読んだ。
- 叩きは約 1.2 秒おきで、予定（約2秒おき、30 回前後）より多かった。不応期 0.8 秒より間隔は長い。
- 記録は確認の後に `data/raw/` から消す。波形は残していない。

## #16 record.py の終了後、端末の入力が表示されなくなる

現象: `tools/record.py` が終わった後（`--duration` の自動終了でも Ctrl-C でも）、端末に打った文字が表示されない。
`stty sane` で戻る。#12 の記録（1収集日 7セッション）のたびに起きるので、記録を続ける前に直した。

原因: マーカー入力のループは daemon スレッドで動き、`tty.setcbreak()` で端末を cbreak（エコーなし・行入力なし）にする。
元に戻す `termios.tcsetattr()` はそのスレッドの `finally` にあるが、daemon スレッドはプロセス終了時に `finally` を
実行せずに打ち切られる。メインが先に終わるので、端末は cbreak のまま残る。
同じ場所にもう1つあった（plan のレビューでの指摘、pty で再現。Python 3.12.3）: `o` の後、note を打ち終える前に
メインが終わると、`input()` で待っている daemon スレッドのせいでプロセスが終わらない
（`sys.stdin.read(1)` で待っている場合は終わる）。

直し方（POSIX の経路だけ。`msvcrt` の経路は端末の設定を変えないので今のまま）:

| 直したところ | 内容 |
|---|---|
| 端末の設定の保存と復元 | メインで持つ（`TtyMode`）。`atexit` に登録してから cbreak にし、`finally` で戻す。`TCSADRAIN`（既定の `TCSAFLUSH` は先行入力を捨てる） |
| 入力スレッド | `select`（0.1 秒）＋ `os.read` で読み、ループのたびに終了の印を見て自分で抜ける。バイト列は増分の UTF-8 デコーダで文字にする |
| `o` の note | 元の設定に戻した間に1行読む（端末が行の編集とエコーを受け持つので、打っている文字が見える）。時刻は今までどおり打ち終えた時点の `last_t_ms`。打ち終える前に終了したら、その `o` は記録しない。改行より後ろまで読めた分は通常のキーとして処理する |
| SIGTERM | `SystemExit` に変えて後始末（`finally`）を通す。SIGKILL は扱えない（`stty sane` で戻す） |
| `Session.mark()` | `close()` の後に呼ばれたら書かない。`mark()` と `close()` は同じロックで守る |

記録の形式（`docs/data-schema.md`）、フレームの読み方、マーカーの意味と時刻の取り方、引数、出力先は変えていない。
tty が無いときは、今までどおり端末に触らず入力スレッドも起こさない。

テスト（`tools/test_record_tty.py`、13 件、約 4.7 秒）: pty を開き、子プロセスの stdin/stdout/stderr を slave に
つないで `main()` を動かす。シリアルは偽物（`read()` は少し待って空のバイト列を返す）に、出力先は `tempfile` に
差し替える（`data/raw/` は読み書きしない）。入力を送るのは、子の出力と pty の設定を確かめてから。

| 場合 | 期待 |
|---|---|
| `--duration` で自動終了 / SIGINT | 終了コード 0。終了後の `ECHO`・`ICANON` が実行前と同じ |
| SIGTERM | 端末が元に戻る。終了コード 143 |
| 実行中 | cbreak（`ICANON=False`）。`s` を送ると `events.csv` に `s` の行が1つ |
| `o` → `memo` | note の入力中は `ECHO=True`・`ICANON=True`。`o` の行の note が `memo`。続く `s` も入る（`memo\ns`、`omemo\ns` と一度に送っても捨てない） |
| note を打ち終えないまま終了（`--duration` / SIGINT） | 期限（5 秒）内に終了コード 0 で終わり、端末が戻る。`o` の行は無い |
| `read_frames` が `OSError` / `SystemExit` を出す | 端末が元に戻る |
| 端末を変える前の失敗（`Serial()` が例外） | 端末は元のまま |
| `close()` の後の `mark()` | 例外を出さず、`events.csv` が変わらない |

- 修正前のコードで同じテストを回すと 12 件が落ちる（通る1件は、端末に触らない「`Serial()` が例外」）。自動終了の
  テストは終了後の `ECHO`・`ICANON` が `(False, False)` のままで落ち、note の途中で終了するテストは子プロセスが
  終わらず期限で落ちる。
- 実機での確認（10 秒の記録、終了後にそのまま端末に入力できること、`o` の note を打つ間に文字が見えること、
  `s` などのマーカーが今までどおり入ること）は人が行い、問題は無かった。確認用のセッションは消した。
