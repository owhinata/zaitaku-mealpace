## AUDIO フレーム1個あたりのサンプル数

**実測: 64 サンプル（128 バイト）。** `audio_chunks.csv` の `sample_index` の差分は全区間で 64、
チャンク間の `t_ms` の差は全区間で 4 ms。総サンプル数 ÷ AUDIO フレーム数 = 158400 ÷ 2475 = 64.000。

ボードコア（`mbed_nano` 4.6.0 の `libraries/PDM/src/rp2040/PDM.cpp`）を読んだ結果も同じ。
`decimation` の初期値は 128 だが、`begin()` で `16000 * 128 * 2 > 3250000` のため 64 に落ちる。
`RAW_BUFFER_SIZE`（512）÷（64 / 8）= 64 サンプルが1コールバックぶんで、16 kHz では 4 ms にあたる。

`logger.ino` の `AUDIO_CHUNK = 256` はアプリ側のバッファ設定であって、1フレームのサンプル数ではない。

## baudrate の実測

`monitor` の `baudrate=115200` と `Serial.begin(2000000)` の食い違い（#1 の申し送り）を実測した。
`tools/record.py` と同じ解析（SYNC / len / xor）をする使い捨てスクリプトで、3秒ずつ両方を開いた。

| baud | 受信バイト数 | 正常受信フレーム数 | XOR 不一致数 |
|---|---|---|---|
| 115200 | 115656 | IMU 321 / AUDIO 759 | 0 |
| 2000000 | 115656 | IMU 321 / AUDIO 759 | 0 |

受信バイト数もフレーム数も完全に一致した。**USB CDC ではボーレートが無視される**ことを実測で確認。
`CMakeLists.txt` の `monitor` を 2000000 に揃え、無視される旨のコメントを付けた。
（この2回はどちらも2回目以降のポートオープンなので META は来ない。想定どおり。）

## 詰まった点

- `cmake --build build --target record -- SUBJECT=...` の形は効かない。`$ENV{}` が configure 時に
  評価されるため。`SUBJECT=self ... cmake --build build --target record` の形に直した。
- 10秒で止める手段。tty が無いので Ctrl-C を送れず、`timeout -s INT` は cmake → make → python と
  プロセスを挟むので SIGINT が届く保証がない。届かずにやり直すと、そのたびにポートを開いて
  META を消費してしまう（META は `setup()` で一度だけ送られ、起動後の最初の接続でしか届かない）。
  `--duration` で自分から終わる形にした。
- そのため、書き込みのあと本番の記録まではポートを開かないようにした。CMake の展開結果の確認は
  configure だけで済ませ、環境変数が届くかどうかは `SUBJECT` に不正な値を入れて
  `subject は self か p1` で落ちることで確かめた（この経路はシリアルを開く前に終わる）。
