# 0020 M2 の音の特徴量の式を 8 kHz・25 ms フレーム・stride 25 ms に固定し、docs/decisions/0012 の音の節を M2 について置き換える

日付: 2026-09-24　状態: 採用

docs/decisions/0019「方式」が #21 の plan に委ねた「M2 用に削った音の特徴量の式」を、実機の計測（`firmware/bench/`、合成信号）と収集日1〜3 の中の
交差検証（0014 の手順、収集日4 は見ていない）を通してここに固定する。`analysis/features_m2.py` がこの式の PC 側の実装で、検出器ファームウェア（#24）は
`firmware/bench/` の案2・案3 の移植をこの式のパラメータで流用する。
`docs/evaluation.md` の定義（窓 1.0 秒 / ホップ 0.25 秒、8 行目の特徴量の名前の並び、イベント単位の数え方、合格線）は変えていない。8 行目は編集していない。
docs/decisions/0012 の IMU の節・窓と時刻・無効な窓・正規化と API の節はそのまま使う。0012 の「特徴量」の表のうち MFCC・スペクトル重心・ゼロ交差率の 3 行と、
「上の表が決めていない細部」の音に関わる項目を、**M2 について**この記録の式で置き換える。0012 自体は M1 の定義として残し、`analysis/features.py` は変えていない。
式・定数・受け入れの判断は人が決めた。採否の経緯は Issue #21 のコメントにある。

## 決定

### 音の特徴量の式（`analysis/features_m2.py`、`FEATURE_SET = "m2-0020"`）

| 項目 | M2 の式 | 0012（M1） |
|---|---|---|
| 特徴量の計算に使う音の周波数 | 8 kHz。16 kHz の隣り合う 2 サンプルの平均 `x8[i] = (x16[2i] + x16[2i+1]) >> 1`（int32 で足して算術シフト。PC と装置で同じ整数演算。長さが奇数なら最後の 1 サンプルを捨てる） | 16 kHz |
| 窓 | 1.0 秒 = 8000 サンプル。窓の格子（`t_lo + 0.25 k`）と「開始に最も近いサンプルから固定長」の規則は 0012 のまま | 16000 サンプル |
| フレーム | 長さ 25 ms（200）、stride 25 ms（200、重なりなし）。1 窓 40 フレーム。1 ホップ（0.25 秒 = 2000 サンプル）はちょうど 10 フレーム | 400 / 160、98 フレーム |
| プリエンファシス | 0.97。フレームごとに独立に掛ける（各フレームの `pre[0] = x[0]`） | 窓全体に掛けてからフレームに切る |
| 窓関数・FFT・パワー | Hamming（200）、`n_fft` 256、`|X|² ÷ 256`（129 ビン、31.25 Hz 刻み） | Hamming（400）、512、257 ビン |
| メル・log・DCT | 26 本、0〜4000 Hz、HTK 式、三角フィルタは FFT のビンの周波数で評価し面積の正規化なし、`log(E + 1e-10)`、DCT-II（ortho）の先頭 13（c0 を含む）。40 フレームの平均 | 26 本、0〜8000 Hz、13、98 フレームの平均 |
| スペクトル重心 | MFCC と同じ（プリエンファシス後の）パワースペクトルから `Σ f·P / Σ P`（Hz）。`Σ P < 1e-12` のフレームは 0。40 フレームの平均 | プリエンファシス前の別の FFT から |
| ゼロ交差率 | 8 kHz の 8000 サンプルで、窓内の平均を引いた符号（`≥ 0` を正）の変化回数 ÷ 7999 | 16 kHz、÷ 15999 |
| 音声の値 | int16 を 32768 で割った float32（間引きの後） | 同じ |

- IMU の 14 次元は 0012 のまま（`features._imu_features` をそのまま呼ぶ）。
- 次元数は 29、順序と名前は 0012 の `FEATURE_NAMES` と同じ（`acc_ptp_{x,y,z}`、`gyro_norm_ptp`、`acc_rms_{x,y,z}`、`gyro_rms_{x,y,z}`、`acc_peak_count`、
  `acc_axis_{x,y,z}`、`mfcc_0`〜`mfcc_12`、`spectral_centroid_hz`、`zero_crossing_rate`）。M1 の値と取り違えない目印は `FEATURE_SET = "m2-0020"` で、
  `analysis/m2_norm.json` と検出器のセッションの `meta.json`（`feature_set`。#23）に書く。
- `valid` の規則は 0012 のまま（音声が窓のサンプル数 8000 に満たない窓、IMU の行数が期待の 90% 未満の窓、飛びと交わる窓）。
- フレームの stride を 0019 が例示した 20 ms（退避先 40 ms）ではなく 25 ms（退避先 50 ms）にしたのは、1 ホップ 2000 サンプル（0.25 秒 × 8 kHz）を割り切る
  stride でないと装置の再利用版（ホップごとに新しいフレームだけ計算する）と PC の計算が同じフレームの格子にならないためで（20 ms は 12.5 フレーム/ホップ、
  40 ms は 6.25）、0019「変えてよいもの」（MFCC のフレームの stride）の趣旨の範囲内の変更である。
- 8 kHz は特徴量の計算用の間引きで、マイクの取り込み（PDM 16 kHz）と `docs/data-schema.md` の記録形式（`audio.wav` 16 kHz）は変えない。
  検出器ファームウェアは 16 kHz のスライスを受け取り、間引いてから 8 kHz のリング（1.0 秒 = 8000 サンプル）に入れ、16 kHz の波形は保持しない。

### 正規化の定数（docs/decisions/0019「正規化」の母集団を、この式について具体化したもの）

- 定数（29 次元の平均と標準偏差（÷ n））は `analysis/ei_upload.py` が fit セッション（EI の分類器の fit に使うセッション。収集日1〜3 のうち validation セッションを除いたもの）の
  `valid` な窓の全部から作り、`analysis/m2_norm.json`（`feature_set`、`feature_names`、`mean`、`std`、`stats_sessions`、窓の数、コミット）に書く。
  `std` が 0 の次元は 1 にする（`features.Standardizer` と同じ）。
- EI に投入するのは正規化後の値。装置（#24）と PC の再採点（#22・#23）は同じ定数を使う。収集日4 は母集団に入れない。

## 理由

- **1 ホップを割り切る stride にする。** 0019 の既定の候補は stride 20 ms だったが、20 ms（160 サンプル）は 1 ホップ 2000 サンプルを割り切らない（12.5 フレーム）。
  装置の再利用版（ホップごとに新しいフレームだけ計算する）は、フレームの格子がホップの整数倍で並ぶことが前提で、割り切れないと窓ごとにフレームの位置がずれ、
  PC と装置で同じ格子を作れない。25 ms（200 サンプル、10 フレーム/ホップ）は割り切り、時間の見込みも 20 ms より小さい。
- **フレームごとのプリエンファシス。** 0012 は窓全体に掛けてからフレームに切るため、再利用版は窓の先頭フレームを毎ホップ計算し直していた（#17）。
  フレームごとに独立にすれば、ホップをまたいで持ち越したフレームの値がそのまま使え、PC の全窓の計算と装置の再利用の計算が一致する。
- **重心は同じ FFT から。** 0012 はプリエンファシス前の別の FFT を使っていて、FFT が 1 フレーム 2 回だった（#17: FFT が 1 ホップの 82%）。
  `docs/evaluation.md` 8 行目の名前の並びを保つために重心は残し、同じスペクトルから出す。
- **8 kHz。** 16 kHz のままでは stride 25 ms でも約 250 ms（見込み）で 200 ms に入らない。嚥下音の主成分は 4 kHz 以下（推測。#20 の重心の値は集計値でしか見ていない）で、
  間引きで失う情報より時間の余裕を優先した。間引きを 2 サンプルの平均にしたのは、PC と装置で整数演算だけで同じ値になり、実装が 1 行で済むため
  （単純な間引き（1 つ飛ばし）より折り返しが小さく、FIR より安い）。
- **交差検証で確かめてから固定する。** 0019 のとおり、装置で測る前に固定すると外れたときに二度変えることになる。実機の時間と収集日1〜3 の中の確認を通してから
  固定した。収集日4 は #22 の閾値のために取っておいた。

## 選ばなかった案

- **stride 20 ms（0019 の既定の候補）／40 ms。** 1 ホップを割り切らない（12.5 / 6.25 フレーム）。
- **8 kHz・stride 12.5 ms（50% 重なり）。** 見込み約 246 ms（IMU 込み）で 200 ms を超える。
- **16 kHz・stride 25 ms。** 見込み約 254 ms で超える。
- **重心を落とす（0019 の段 d / f）。** `docs/evaluation.md` 8 行目の並びを変える。時間は 1 フレーム 0.6 ms しか変わらない。
- **窓全体のプリエンファシス（0012 のまま）。** 再利用版で先頭フレームの計算し直しが要る。
- **間引きを FIR の低域通過にする。** 折り返しは減るが、装置の時間と実装が増える。差が効くかは分からない。
- **メルの本数・係数の数を減らす。** 時間はほとんど変わらない（メル＋DCT は 1 フレーム 2 ms）。日ごとのずれ（#20）の対策は EI の学習側で見る。

## 確かめていないこと

- 割り込み（PDM・IMU・USB CDC）が動いている状態の時間（#24 で測る）。推論と送信の時間。
- 実信号での間引きの影響（合成信号でしか答え合わせしていない。日をまたぐ動きは収集日1〜3 の交差検証でしか見ていない）。
- 窓の開始サンプルの偶奇による PC と装置の 1 サンプル（62.5 µs）のずれ。M1 の「開始に最も近いサンプル」の規則と同じ種類のずれで、平均した MFCC には効かない見込み。
