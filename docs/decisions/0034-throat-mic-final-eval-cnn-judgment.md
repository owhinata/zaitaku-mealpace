## 決定

1. #40 は評価側（収集日 2 = 2026-10-12 の 7 本。0032「最後の 1 収集日」）を **1 回だけ**採点し、その 1 回で事前に登録した 2 つの構成の数字を出す。
   - **構成 J（M3 の判定に使う）**: CNN、入力 `mfe40`、乱数の種 0、構成と学習は 0033 §2 のまま（Conv 1→8→16→32、Adam 1e-3、バッチ 64、
     20 エポック、陽性の重み = 陰性数 ÷ 陽性数、決定的、4 スレッド）、後処理 ヒステリシス 入り 0.95・出 0.85。
   - **構成 R（M1 と同じ手法の参照）**: `a52` ＋ ロジスティック回帰（0014 の設定）＋ ヒステリシス 入り 0.85・出 0.65。

   M3 の判定（0024 の M3 (3)、#41）は構成 J の数字で読む。構成 R は M1 と同じ手法（手作り特徴量＋ロジスティック回帰）の参照として並べる。
2. どちらも学習側の全 14 本で学習し直す。正規化（LR は `features.Standardizer`、CNN はメルの帯域ごとの平均と標準偏差）・陽性の重みは
   学習側だけで作る。閾値・ヒステリシス・組・種は選び直さない（0033 の学習側 CV で決まった動作点のまま）。
3. CNN の種は 0 だけ。種 1・2 は評価側で採点しない（事前に登録した構成ではないため）。

   3b. **初回の採点は 1 回。** 入口（`analysis/final_eval.py`）は印のファイル `docs/log/m3-final-40.txt` があれば止まる。印は、学習が済んで
   評価側を開く直前に固定のパスへ排他作成（`O_EXCL`）し、書き込み・fsync・close の後に評価側を開く。印は、その後の手順で止まっても消さない。
   再実行の引数（`--reproduce` など）は作らない。再現を確かめたいときは、初回の採点に使ったコミット（印に書いたコミット）の別 worktree
   （印・図・log のコミットより前なので印が無い）で、同じ入力（元の `data/raw/` を絶対パスで渡す。`data/raw/` には何も書かない）・
   同じ依存の版・同じ環境で同じコマンドを走らせ、元の log に「再現の実行（初回のコミットの別 worktree）」として記録する
   （印と git の検査は変えない。人が行う故意の経路で、運用で扱う）。worktree の中で作られた印と図は worktree ごと捨て、コミットしない。
   再現の実行の数字は、#41 の数字の差し替えにも、構成・閾値・種の選択にも使わない。初回と差が出たら、差を記録して人に渡す
   （CNN は PyTorch の版・CPU をまたいだ一致を保証しない。0033 §6）。
4. 機械が読む固定値の行。`analysis/final_eval.py` が実行時にこの記録の `FINAL-` で始まる行を読み、コードの定数（`CONFIGS`・`EXPECTED_TRAIN`・
   `EXPECTED_EVAL`）と一字一句一致しなければ、データを開かずに止まる。セッション名は `self` のフォルダ名で、すでに公開の log

## 理由（学習側 CV の事実。docs/log/2026-10-12.md「#43 段階 2」）

- CNN（`mfe40`）のヒステリシスの学習側 CV の誤検出率は種 0・1・2 で 0.83・1.44・1.20 回/分、LR の 8 行は 1.95〜2.69 回/分。
  検出率はどれも 1.000（67/67）か近い値。種による揺れ（0.83〜1.44）はあるが、3 つの種のどれも LR のどの行より低い。
- 陽性窓の割合は CNN 0.039〜0.046、LR 0.04〜0.08。CNN の誤検出の少なさは、陽性を出し続ける効果（0011「既知の弱点」）ではない。
- 推論は numpy の順伝播で PC 1 窓 1.05 ms（中央値、1 スレッド）。学習は PC だけ（PyTorch CPU）。装置（UNO Q の Linux 側）で同じ numpy の
  コードを使う前提（0025）は変わらない。UNO Q での時間は未確認（M4）。
- 評価側はまだ開いていないので、今変えても「評価側を見てから変えた」ことにはならない（0003・0014 の理由は保たれる）。

## 事前登録と、後から選ばないこと

- 2 つの構成は評価側を開く前にこの記録とコードの定数で固定する。評価側の数字を見た後に、どちらを判定に使うかを入れ替えない。
- 構成 R が合格線を満たし構成 J が満たさない場合も、判定は構成 J の数字で読み、構成 R の数字は参照として並べるだけ（逆の場合も同じ）。
- 評価側の数字を見た後に、閾値・後処理・種・組を変えて評価側を採点し直さない。

## 選ばなかった案

- **構成 R（`a52`）だけ**（#43 の元の受け渡し）: 学習側 CV で CNN の誤検出率が種を問わず低いという事実を判定に使わないことになる（人）。
- **構成 J（CNN）だけで、参照を出さない**: M1 と同じ手法の数字が無くなり、M1・M2 と並べる手掛かりが消える。
- **評価側を見てから 2 つのうち良いほうを選ぶ**: 評価側を選択に使うことになる（0003・0014）。
- **CNN の種 0・1・2 を評価側で全部出す**: 事前に登録していない構成を評価側で見ることになり、見た後に種を選ぶ余地が生まれる。
- **再実行の引数（`--reproduce`）**: 「1 回だけ」と両立させる仕組みが要る。再現は初回のコミットの別 worktree で行う（上の 3b）。

## 評価側を学習側に戻さない検査（ステップ 1 の adversarial-review の指摘による。人の決定 10/12 夜）

- 後日 `data/raw/` にセッションを足すと、`split_sessions(kind="throat")` の分割が動き、上の `FINAL-EVAL` の 7 本が学習側・交差検証に入りうる
  （`train_eval.py --throat`・`compare.py`・`visualize.py` は分割を計算し直す）。そうなると評価側を見た後に構成・後処理・種を比べ直せるので、
  `analysis/fixed_eval.py` の `assert_fixed_eval_not_in` で止める: `FINAL-EVAL` の 7 本（定数 `EXPECTED_EVAL`）のどれかが学習側の一覧にあれば、
  データを読む前に止まる。呼ぶ場所は `train_eval.run()` の咽喉マイクの経路・`compare.run()`（どちらも分割の直後）と `visualize.py` の学習側の
  名前の検査（`check_sessions`。単体の CLI を含む）。M1 の経路（`kind="m1"`）には当てない。
- 印 `docs/log/m3-final-40.txt` があるとき、`train_eval.py --throat` と `compare.py` の報告の冒頭に「評価側は採点済み（印あり）。この実行は学習側だけ」の
  1 行を出す（どちらも評価側を開かない）。
- `fixed_eval.py` は固定の一覧・印のパス・検査だけを持つ軽いモジュール（標準ライブラリだけ）で、`final_eval.py` もここから一覧を読む。
