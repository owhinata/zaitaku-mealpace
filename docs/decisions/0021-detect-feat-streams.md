# 0021 検出器の DETECT / FEAT ストリームの形式と、検出器セッションの記録の範囲

日付: 2026-09-24　状態: 採用

検出器ファームウェア（#24）が PC に送るフレームの形式、`tools/record.py` が書くファイル、`analysis/evaluate_detector.py` の数え方の前提をここに固定する（#23）。
`docs/data-schema.md` に DETECT / FEAT、`detect.csv`、`feat.csv`、検出器の `meta.json` を足した。既存のファイル・列・単位・フレーム形式は変えていないので、
記録済みのセッションの変換は要らない。`docs/evaluation.md` の定義と合格線は変えていない。docs/decisions/0011 が決めた「記録の範囲」に、検出器のセッションの
読み方を 1 つ足す（下の「記録の範囲」）。docs/decisions/0019 が #23 に求めた要件（FEAT は正規化前の値、次元数と順序は音の式の記録に従い `meta.json` に
`feature_names`、DETECT の確率は `swallow` のみ）と、docs/decisions/0018 の `led` の値（0 / 1 / 2）に従う。形式の細部は人が決めた。採否の経緯は Issue #23 のコメントにある。

## 決定

### フレーム

- ヘッダは今までの形式のまま（`[0xA5 0x5A][id u8][len u16 LE][t_ms u32 LE][payload][xor u8]`）。`stream_id` を 2 つ足す。
  `0x04` DETECT（ペイロード 10 B: `window_t_ms` u32、`prob` float32、`positive` u8、`led` u8）と `0x05` FEAT（`window_t_ms` u32 ＋ float32 × N）。
- ヘッダの `t_ms` は送信時刻（送るときの `millis()`）。窓の開始はペイロードの `window_t_ms`。マーカーの `t_ms` は今までどおり直前に届いたフレームの
  ヘッダの `t_ms`（送信時刻）で、`window_t_ms` にしない（窓の開始にすると、マーカーが押した時刻より 1 秒以上早くなる）。
- `prob` は float32。装置が閾値と比べた値をそのまま残し、PC 側で `positive == (prob >= threshold)` を丸めなしに確かめられるようにする。
  `cough` の確率・クラスは載せない（0019）。
- FEAT の値は float32。装置が正規化する前の値（物理単位）。次元数 N はフレームの長さから決まり、名前と順序は `meta.json` の `feature_names`（装置の META フレームの
  申告値）。次元数の確定は音の式の記録（#21）。
- 検出器の META フレームは `fw`（`detector`）、`imu_hz`、`audio_hz`、`window_ms`、`hop_ms`、`threshold`、`model`（EI のプロジェクト ID と deploy version）、
  `feature_set`（音の式の記録の番号）、`feature_names` を持つ。`record.py` は今までどおりトップレベルに merge する（0006）。
- 検出器は `0x02` AUDIO を送らない（0005）。FEAT は変換後の特徴量で、0005 が禁じる「生の音声波形の保存・送信」に当たらない。ただし生の計測データとして扱い、
  `data/raw/` の外に出さず、コミットしない。`self` のセッションで有効にし、`p1` で使うかは別に決める。

### `tools/record.py`

- `detect.csv`（`t_ms, window_t_ms, positive, prob, led`）と `feat.csv`（`t_ms, window_t_ms, f0..f(N−1)`）を書く。`prob` も特徴量も有効数字 9 桁
  （float32 が往復で一致する桁数。`prob` は閾値との比較を PC 側で丸めなしに再現するため）。
- ストリームのファイルは、そのストリームの最初のフレームが届いたときに作る（`analog.csv` と同じ）。`events.csv` と `meta.json` は常に作る。
  検出器のセッションには `detect.csv`・`feat.csv`・`events.csv`・`meta.json` だけができる。記録ファームウェアのセッションは、フレームが届けば今までと同じ
  ファイルが同じ内容でできる。変わるのはフレームが 1 つも届かなかったセッションだけ（空の `imu.csv`・`audio_chunks.csv`・`audio.wav` ができなくなる）。
- 引数、出力先の固定（0007）、マーカーの取り方、端末の扱い（#16）は変えない。

### 記録の範囲（docs/decisions/0011 の読み替え。検出器のセッションだけに適用する）

- 検出器のセッションには `imu.csv` と `audio_chunks.csv` が無い。記録の範囲は `detect.csv` と `feat.csv` の時刻から取る。始まりは `detect.csv` の最初の行の
  `window_t_ms`（装置の最初の窓の開始）。終わりは、`detect.csv` の全行の `t_ms`、`detect.csv` の全行の `window_t_ms + 1000`、`feat.csv`（あれば）の全行の `t_ms` の最大
  （最後の窓の終端か、最後に届いたフレームの送信時刻の遅いほう）。
- 終わりに両方のストリームの送信時刻を含めるのは、マーカーの `t_ms` がストリームを問わず直前に届いたフレームの送信時刻であり、送信時刻は窓の終端より処理の分だけ
  後になるため。最後の窓の終端や `detect.csv` の送信時刻だけで切ると、最後のフレーム（DETECT → FEAT の順なら FEAT）の後に打ったマーカーが範囲の外になる。
  0011 が「マーカーは直前に届いたフレームの `t_ms` を使うので IMU だけの範囲にしない」と決めたのと同じ理由。
- 送信の遅れの上限: 全行で `t_ms − (window_t_ms + 1000)` が 1000 ms（`MAX_SEND_LAG_MS`。`evaluate.MAX_GAP_MS` と同じ値）以下であること。超えたセッションは
  範囲を出さずにエラーにする。単調性と隣との差の検査だけでは、送信の遅れが少しずつ増える装置で非嚥下区間が伸び、誤検出率の分母が薄まるのを防げない。
  この上限により、送信時刻で伸びる非嚥下区間は 1 セッションに 1 回、1.0 秒以下。#24 の実測を見て上限を詰めるかは人が決め、この記録に追記する。
- `detect.csv` と `feat.csv` のそれぞれで、`window_t_ms` は狭義に単調増加、`t_ms` は単調非減少で、どちらも隣との差が 1000 ms を超えないこと。外れたセッションは
  範囲を出さずにエラーにする（0011 と同じ）。範囲より前のマーカー（`t_ms = 0`、META だけが届いた後）は 0011 のとおりエラー。
- `feat.csv` の窓は `detect.csv` の窓の部分集合であること（`--scorer` の有無によらず）。`detect.csv` に無い窓が `feat.csv` にあれば範囲を出さずにエラーにする
  （DETECT より長く続く FEAT で非嚥下区間が伸びる経路を閉じる）。`detect.csv` にあって `feat.csv` に無い窓は数えて報告に出す。
- 閾値との比較は float32 で行う。装置は閾値を float32 の定数として持ち、META にはその値を有効数字 9 桁で書く。PC は `prob`（`.9g` で往復した float32）と、`meta.json`
  の `threshold` を float32 に丸めた値を比べる（`positive != (prob >= threshold)` の検査と `--scorer` の PC の陽性）。
- 陽性窓は `positive == 1` の行の `window_t_ms`。数え方（検出、誤検出の塊、非嚥下区間、合算、混同行列）は 0011 のまま `evaluate.event_metrics` と
  `evaluate.aggregate` を使う。`led` と `prob` は評価に使わない。
- `analysis/split.py` は `meta.json` の `fw` が `detector` のセッションを M1 の分割（`train` / `eval`）に入れない（戻り値の `detector` に列挙する）。`fw` が
  `detector` でないのに `detect.csv` か `feat.csv` があるセッションは止める（META が届かなかった検出器のセッションは消す。`docs/recording-protocol.md`）。
  `fw` が無い記録ファームウェアのセッション（0006）は今までどおり分割に入れる。

### `tools/check_session.py`

- `detect.csv`・`feat.csv` のセッションでは `window_t_ms` の飛び（公称 250 ms の 1.5 倍以上）から取りこぼしを推定し、1% 未満を基準内とする（#7 の作業上の基準。
  `docs/evaluation.md` の合格線ではない）。`t_ms` の逆行、最大差分、送信時刻 − 窓の開始（`t_ms − window_t_ms`）、DETECT と FEAT の窓の不一致も出す。
- `positive`・`prob`・`led` の集計は出さない（採否を決める前に陽性を数えない。`docs/recording-protocol.md`）。

### `analysis/evaluate_detector.py`

- 既定の対象は `self` の `meal` で `fw` が `detector` のセッション全部。`--sessions` で明示したときはそれだけ（除外を報告に出す）。評価に使うセッションの
  `threshold`・`model`・`feature_names` は一致していなければ止める（同じファームウェアで録ったセッションだけを合算する）。
- 既定の実行は `evaluate.aggregate` を通す（3 セッション未満は止まる）。`--sessions` で 3 セッション未満のときはセッションごとの数字だけを出し、
  合算を出さないと明記する（#24 の 60 秒の確認のため。M2 の数字ではない）。
- 参考値: 常時陽性の場合の数字、陽性窓の割合（0011「既知の弱点」）、`positive != (prob >= threshold)` の行数、`c` に紐づく誤検出の塊（塊の最初の窓の中心 − `t_c` が
  `[−1.0, +5.0]` 秒。#20 の定義）、収集日ごと・会話の有無ごと（`o` の note `conv`）の合算。式は `train_eval.sum_metrics`。
- `--scorer PATH`: `score(features, meta) -> 確率の列` を持つ Python ファイルで `feat.csv` を再採点し、装置の `positive` との差（装置 1 / PC 0、装置 0 / PC 1、
  `|prob − prob_pc|` の最大）と PC の陽性で数えた数字を出す。閾値は `meta.json` の `threshold`（装置の申告値）で、上書きの引数は置かない。scorer の中身は #22。

## 理由

- **ヘッダを変えない。** `record.py` の読み方（`read_frames`）と記録ファームウェアの送信をそのまま使える。ストリームの追加は `docs/data-schema.md` が
  最初から想定していた経路（「ストリームを足すときは `stream_id` を増やす」）。
- **確率を float32 で運ぶ。** 差の切り分け（#22・#24・#27「装置の出力と PC の再採点の差」）で、丸めの規則を疑わなくてよい。帯域は 4 Hz で問題にならない。
- **特徴量を正規化前の float32 で運ぶ。** 0019 の要件。次元ごとのスケールを `meta.json` に持たなくてよい。
- **次元数をフレームの長さと `meta.json` から取る。** 音の式（#21）の確定を待たずに #23 を進められ、式が変わっても PC 側のコードを変えなくてよい。
- **ファイルを最初のフレームで作る。** 検出器のセッションに空の `imu.csv`・`audio.wav` を作らない（#26 の記述と一致）。記録ファームウェアの出力は変わらない。
- **記録の範囲の終わりに両方のストリームの送信時刻を含め、送信の遅れに上限を置く。** マーカーの取り方を変えない（#26 の要求）まま、範囲の外のマーカーのエラーを
  避け、送信の遅れで非嚥下区間が伸びる経路を閉じる。
- **`fw` で見分ける。** #26 が「`fw` が `detector` であること」を採否の材料にしており、装置の申告値を正とする 0006 と一致する。cond やファイルの有無で
  分けると、文書と実装の判断基準が二重になる。
- **`check_session.py` が陽性を出さない。** 採否は数字を見る前に決める（#26、#27）。

## 選ばなかった案

- **`prob` を u8（0〜255）にする（Issue #23 の本文の案）。** 丸めの規則が要り、閾値付近の行で PC の比較がずれる。u16 も同じ。
- **FEAT を int16 のスケール付きにする。** 次元ごとのスケールが `meta.json` に要る。帯域は問題にならないので float32 でよい。
- **`led` を DETECT に載せない（PC で再計算する）。** 0018 が装置の `led` 列と再計算の一致を #25 で確かめると決めている。
- **窓の連番をフレームに足す。** `window_t_ms` の差分で飛びを数えられる（`check_session.py`）。Issue に無い。
- **`window_t_ms` をマーカーの時刻にする。** マーカーが 1 秒以上早くなる（#26）。
- **記録の範囲の終わりを最後の窓の終端にする。** 最後のフレームの後のマーカーが範囲の外になる。**最後の窓の開始にする。** 最後の窓のデータを範囲から落とす。
  **`detect.csv` の送信時刻だけを含める。** 最後に届くのが FEAT なら、その後のマーカーが範囲の外になる。
- **FEAT の窓を DETECT と突き合わせない。** DETECT より長く続く FEAT があると、時刻の検査を全部通ったまま非嚥下区間が伸びる。
- **閾値を float64 のまま比べる。** 装置は float32 で比べるので、装置で等しい行が PC では小さく見え、`positive` との不一致が出る。
- **送信の遅れに上限を置かない。** 遅れが少しずつ増える装置で非嚥下区間が伸びるのを検査で止められない。**上限を #24 の設計値 250 ms にする。** 実測前で、
  一時的な遅れでセッションが使えなくなる恐れがある。実測後に人が詰める。
- **`split.py` で cond が `meal` のセッションを外す。** `meal` を記録ファームウェアで録ることを文書は禁じておらず、装置の申告値で見分けるほうが #26 と一致する。
  **`fw` が無いセッションを止める。** M1 の 28 本に META が届かなかったセッションがある可能性を排除できない（0006）。
- **検出器のセッションで空の `imu.csv` と `audio.wav` を作る（今の `record.py` のまま）。** #26 の「`detect.csv`・`feat.csv`・`events.csv`・`meta.json` だけができる」
  と食い違い、`check_session.py` が空ファイルの扱いを持つことになる。**作ってから空なら消す。** 動きが分かりにくい。
- **`evaluate_detector.py` に閾値の上書きの引数を置く。** 凍結した閾値（#22）と違う値で数字を出す経路になる。
- **`-dirty` で止める（`train_eval.py --final` と同じ）。** #24 の作業中の確認で何度も走らせる。#27 はコミット済みの状態で走らせる手順にする。

## 確かめていないこと

- フレームが実機で 0.25 秒ごとに届くか、`t_ms − window_t_ms`（処理の遅れ）の実際の値（#24 の 60 秒の記録で `check_session.py` の出力から確かめる）。
  マーカーの `t_ms` と押した時刻の差は `record.py` が PC 側の時刻を記録しないので `check_session.py` からは分からず、確かめる方法は #24 の plan で別に決める
  （#26 の「打つマーカー」の丸めの記述の前提）。送信の遅れの上限 1000 ms が実機の値に対して緩すぎるか（詰めるかは #24 の log を見て人が決める）。
- 装置のホップの揺れ。`window_t_ms` の間隔が 375 ms を超えると、`check_session.py` は飛びと数え、`evaluate.event_metrics` は陽性の連続を 2 つの塊に分ける
  （厳しい側。docs/decisions/0014「無効な窓の効果」と同じ向き）。
- META の JSON（`feature_names` を含めて 600 B 前後）を 1 フレームで送って `record.py` が受けられること（受信の経路は長さに依存しないが、実機では未確認。#24）。
- #22 の scorer が `score(features, meta)` の形に収まるか（PC 上で EI の C++ ライブラリを呼ぶ手段は #22 が決める）。
