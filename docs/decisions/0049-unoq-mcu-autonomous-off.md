## 決定

1. **0035 決定 7 の消灯を改める。** 0035 決定 7 の「受け取った状態をそのまま画にするだけで、表示の規則（0018 の保持、更新が 1.0 秒無ければ消灯）は持たない」のうち、
   消灯について改める: MCU は、`loop()` が `zm_set_state` の受信に気づいてから約 2 秒（2000 ms 以上。main スレッドの `millis()`）次の受信に気づかなければ、
   自分でマトリクスを全消灯にする。
   - 起点は RPC のハンドラが受けた時刻ではなく、`loop()` が受信の数の変化を見た時刻（`firmware/unoq_mcu/rx_hold.h`）。受けるたび（範囲外の値・状態 0 を含む）に起点を取り直す。
   - 時間切れの後は、次の受信に気づくまで消灯を保つ（`millis()` の約 49.7 日の一周で再点灯しない。コミット前の adversarial-review の指摘、11/3）。
   - 消灯の後に受信に気づけば、その状態を出す。起動から一度も受けていない間は消灯（今までと同じ）。
   - 受信から `loop()` が気づくまでの遅れは切り分けて測らず、上限も決めない（実機では操作から消灯までの全体の時間を目視で確かめる）。
2. **保持は持たない。** 0018 の表示の規則（陽性窓から 2.0 秒の保持、窓の結果が 1.0 秒出なければ消灯）は今までどおり Linux 側（`device/unoq/detector.py`・`analysis/led_rule.py`）だけが持つ。
   MCU の消灯（`loop()` が受信に気づいてから約 2 秒）は「Linux から状態が届かない」ときの消灯で、0018 の 1.0 秒の規則とは別のもの
   （表示器の「状態が 1.0 秒届かなければ消灯」（0018 の #29 の追記）と同じ種類の規則で、時間だけが違う）。
3. **Linux 側の送り方は変えない。** Linux 側は、窓が処理されて RPC が通っている間は、窓ごと（0.25 秒ごと）に状態が変わらなくても `zm_set_state(led)` を送る
   （今の `detector.py` のまま。0035 の追記 #47 の形。`device/unoq/test_detector.py` の `test_r1`・`test_r11`）。新しい送り直しは足さない。
   RPC が失敗したとき・つなぎ直し（`RPC_RETRY_S` 1.0 秒）の間・窓の処理が遅れたときに、MCU が受ける間隔がどうなるかは保証しない（実機の結果として下に書く）。
4. **ハートビートと並べて使う。** PC と Linux の間のハートビート（0037 の追記 10/29: 0.5 秒ごと、2.0 秒で検出器が消灯して止まる）は変えない。消灯の経路は 3 つになる:
   - PC と Linux の間 → ハートビート（Linux が消灯を送る）。
   - Linux の中で窓が止まる → `IDLE_OFF_S` 1.0 秒（Linux が消灯を送る）。
   - Linux と MCU の間（検出器の `kill -9`、`arduino-router` の停止、Linux の停止）→ MCU（`loop()` が最後の受信に気づいてから約 2 秒）。
5. **値は unoq_mcu だけの定数。** `firmware/unoq_mcu/rx_hold.h` の `UNOQ_RX_OFF_MS = 2000`。共有の `firmware/detector/led_rule.h`（`firmware/indicator/led_rule.h`・
   `firmware/unoq_mcu/led_rule.h` はこれへのリンク）の `LED_OFF_TIMEOUT_MS`（1000）と `led_off_due` は変えない（M2 の検出器・表示器の 1.0 秒に触れない）。
6. **`led_check.py` の文言を直す。** MCU が消すので、`led_check.py wave`・`smile` の表示は約 2 秒で消える。文言の「表示の規則はまだ無い」を消し、
   「MCU は次の状態が約 2 秒届かなければ消します」を足した。送る値・引数・`bench` は変えない。配るファイルなので H 行の `code_sha256` が変わり、配り直しが要る。

## 理由

- Linux と MCU の間が切れると、古い目安（微笑む顔・波線）が見え続け、動いていない装置の目安を介助者が信じてしまう（0018「消灯の規則を置く」と同じ理由）。
  PC と Linux の間はハートビート（#47）で塞いだが、Linux と MCU の間は塞いでいなかった（0042 の指摘 2）。#53 の自動起動では PC がないので、Linux と MCU の間で消灯を出せるのは MCU だけ。
- 約 2 秒（2000 ms）は、窓が処理されて RPC が通っている間の送信の間隔（窓ごと、0.25 秒）より十分に長く、ハートビートの 2.0 秒とそろう（0042「2 秒程度」）。
  RPC の失敗・つなぎ直しの間に消えるかどうかは保証しない。
- 古い目安が残りうる長さは、`loop()` が最後の受信に気づいてから約 2 秒。
- 時刻は main スレッドだけが取る（ハンドラは受信の数を 1 つ増やすだけ）。ハンドラと `loop()` が共有するのは状態と受信の数の 2 つの `std::atomic` だけ（`led_out.cpp`）。

## 選ばなかった案

- 共有の `led_rule.h` に時間を引数で受ける関数を足す（共有のファイルに触れる）。
- 共有の `LED_OFF_TIMEOUT_MS` を 2000 にする（M2 の検出器と表示器の 1.0 秒が変わる）。
- unoq_mcu も 1000 ms を使う（つなぎ直しの 1.0 秒と近く、RPC の失敗があると消えやすい。0042 の「2 秒程度」と違う）。
- Linux 側でメインのループから 0.5 秒ごとに送り直す（窓が出ている間は窓ごとの送信と重なり、窓が止まった間は 1.0 秒の消灯が先に効く）。
- MCU が 0018 の保持まで持つ（Linux と MCU で同じ規則を二重に持つことになり、0025 の「推論と規則は Linux 側の Python」と合わない）。
- `led_check.py` に表示し続けるモードを足す（Issue にない）。

- `device/unoq/detector.py`・`DEPLOY_FILES`、`analysis/`、`tools/`（`record.py` の後始末の `led_check.py off` も残す）。
- M4 の数字には影響しない（評価用 `meal` は `--no-rpc` で、LED は評価に使わない。0018・0037 の追記 10/29）。0037 の 5「途中で装置の構成やプログラムを書き換えたら、それより前の評価用 `meal` は
  M4 の数字に使わない」の期間は、評価用 `meal` の打ち切り（11/1 の終わり）、評価側の 1 回だけの採点（11/1、印 `docs/log/m4-final-49.txt`、0041）と関門の判定（0042、11/1）で終わっている。
