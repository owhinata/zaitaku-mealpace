# 0006 `docs/data-schema.md` の記載を実物に合わせ、サンプルレートの正を決める

日付: 2026-09-19　状態: 採用

## 決定

### 1. `docs/data-schema.md` の記載漏れを埋める（記録形式は変えない）

- セッションフォルダの一覧に `audio_chunks.csv`（`t_ms, sample_index`）を足した。
  同じ文書の「audio.wav」節には以前から書かれていて、`tools/record.py` も実際に作っていた。
  一覧だけが落ちていた。
- `meta.json` の例に `fw` / `imu_hz` / `audio_hz` を足した。`tools/record.py` が装置の META
  フレームをトップレベルに merge するため、実物にはこの3つが入る。

どちらもファイル名・列・単位・フレーム形式を変えていない。記載を実物に合わせただけで、
記録済みのセッションを変換する必要はない。

### 2. サンプルレートは装置の申告値を正とする

`meta.json` にはサンプルレートが2か所に出る。

| 場所 | 出どころ | 意味 |
|---|---|---|
| `sample_rates` | `tools/record.py` が組み立てる | PC 側の既定値 |
| トップレベルの `imu_hz` / `audio_hz` | 装置の META フレーム | 装置の申告値 |

- **装置の申告値（トップレベルの `imu_hz` / `audio_hz`）を正とする。** 実際にサンプルを作って
  いるのは装置であり、`sample_rates` は装置が黙っているときの PC 側の当て推量だから。
- `sample_rates` は「装置が META を送らなかった場合の既定値（fallback）」と位置づける。
- 解析側は、トップレベルの値があればそれを使い、無ければ `sample_rates` を使う。

### 3. まだ実装しないこと（将来の案）

次の2つは案として記録するだけで、`#2` では実装しない。

- 記録時に2つの値の不一致を検出して警告を出すこと。
- fallback を使ったセッションであることを、解析側が記録すること。

**`meta.json` の `notes` に何かを書き残すとは決めない。** 現在の `tools/record.py` は `notes` を
空文字で初期化するだけで、書き換える経路が無く、装置の META フレームにも `notes` は含まれない。
実装に無い挙動を文書が約束しないようにする。

## 理由

- `#2`（実機に書き込み、PC でフレームを受信できることを確認する）で10秒の記録を取り、
  できたフォルダと `meta.json` を実物と突き合わせたところ、上の2点の記載漏れが見つかった。
  `docs/data-schema.md` は「この文書を変えるときは `docs/decisions/` に記録を残す」と定めている。
- サンプルレートが2か所に出ること自体は実装の成り行きだが、どちらを読むかを決めておかないと、
  解析側が場当たりに選んでしまう。M1 以降で窓を切るときにレートは効くので、先に決めておく。

## 追記（2026-10-01、Issue #33）: META を記録の開始時に合図で受け取る

装置は起動時に META を 1 回だけ送り、ポートが開かれていないときの送信は捨てられる（mbed_nano の `SerialUSB::write()`）。
起動後に別の相手が先にポートを開くと、その後に `tools/record.py` を始めても META が届かず、`meta.json` に `fw`・`threshold`・
`model`・`feature_names` が入らないセッションができた（#25、#32 で録り直し）。これを次のように直す。記録の形式は変えない。

- 合図: `record.py` は検出器のポートを開いた直後に 1 バイト `M`（0x4D）を 1 回書く。フレームではない（SYNC も長さも無い）。
  合図は記録の開始時の 1 回だけで、記録の途中では送らない。
- 検出器: `loop()` の先頭で 20 ms ごとに受信を確かめ（1 回に最大 64 バイト）、`M` を受けたら `setup()` で作った同じ META を 1 回送り直す
  （1 回の確認で `M` が何個あっても 1 回）。他のバイトは捨てる（送り返さない、保存しない）。起動時の 1 回の送信は残す（挿し直してから
  始めた場合も今までどおり届く）。META の JSON の中身と送るフレームの種類（META・DETECT・FEAT）は変えない。
- `record.py` は合図の後、最長 5 秒（`META_WAIT_S`）次の META を待ち、受けてからセッションのフォルダを作って記録を始める:
  XOR が合い、UTF-8 の JSON の辞書で、`fw` が空でない文字列。満たさない META は届かない扱いで待ち続ける。
  `fw` が `detector` なら `threshold`（数値）・`model`（辞書）・`feature_names`（空でないリスト）がそろっていること。欠けていれば止まる
  （装置の META は送り直しても同じなので待ち続けない）。`--cond meal` では `fw` が `detector` であることも条件にし、違えば止まる。
  値の正しさ（`feature_names`・`model` が scorer と一致するか）は今までどおり評価のときに `analysis/` が見る。
- 届かない、合図が書けない、ポートが開けない、上の条件で止まる、待つ間に Ctrl-C のときは、記録を始めずに終了コード 1 で止まり、
  フォルダを作らない。
- 待つ間に届いた META 以外のフレームは記録の開始前のもので、書かない・数えない。記録は META を受けた後に届いたフレームから始まる
  （`record.py` を少し遅く始めたのと同じ。記録の範囲の定義（0011・0021）と `docs/evaluation.md` は変わらない）。META の後ろに同じ読み取りで
  届いたバイトは記録に引き継ぐ。
- `meta.json` に合図で受けたことは書かない（形式とキーを変えない。`meta.json` があれば META は届いている）。
- 挿し直した直後は起動時の META と合図への META の 2 つが届きうる。2 つ目は同じ内容で merge されるので `meta.json` は 1 つのときと同じで、
  終了時の表示が `META: 2` になる。
- 記録ファームウェア（`firmware/logger/`）は合図に応えない。logger で録るときは今までどおり記録の前に USB を挿し直す（届かなければ止まる）。
