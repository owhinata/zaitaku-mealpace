## 決定

### 方式（Issue #18 の候補 5 の派生。以下「装置特徴量＋EI 分類器」）

- 検出器ファームウェアが、`docs/evaluation.md` の窓（1.0 秒 / ホップ 0.25 秒）ごとに、IMU と音の特徴量を自前で計算し、1 本の特徴量ベクトルにする。
  Edge Impulse（以下 EI）の DSP ブロックは使わない（impulse の処理ブロックは Raw data の素通し。受け付けの形は #21 の最初に確かめる）。
  EI は分類器（int8）の学習・量子化・C++ ライブラリ形式の書き出し（docs/decisions/0001）に使う。推論はその C++ ライブラリで行う。
- IMU の特徴量は docs/decisions/0012 の 14 次元をそのまま使う（#17 案3: 1 ホップ 8.1 ms）。
- 音の特徴量は 0012 の 15 次元をそのまま載せない（#17 案2: 1 ホップ 1099 ms。250 ms の 4.4 倍）。M2 用に削った式を、この記録とは別の記録
  （0012 の音の節を M2 について置き換える記録。0012 自体は M1 の定義として残す）に固定してから使う。削る方向と制約は次のとおり。
  - 変えてよいもの: 特徴量の計算に使う音のサンプリング周波数（16 kHz → 8 kHz への装置上の間引き。マイクの取り込みと記録形式は 16 kHz のまま）、
    MFCC のフレームの stride（10 ms → 20 ms、または 40 ms）、スペクトル重心の出し方（MFCC と同じプリエンファシス後の FFT から出す）、メルの本数と係数の数。
  - 変えないもの: 窓 1.0 秒 / ホップ 0.25 秒、`docs/evaluation.md` 8 行目の特徴量の名前の並び（既定の候補と退避先では保つ）、IMU の 14 次元、
    MFCC の枠組み（フレーム化 → Hamming → FFT → メル → log → DCT）、ゼロ交差率、ラベルの規則（下）、生の音声を保存も送信もしないこと（docs/decisions/0005）。
  - 既定の候補: 8 kHz・重心は MFCC と同じ FFT から・stride 20 ms（#17 の段階ごとの実測からの見立てで 1 ホップ 約 170 ms。実測ではない）。実機で特徴量の計算
    （IMU ＋ 音）が 1 ホップ 200 ms（250 ms の 8 割。作業上の目安で評価の定義ではない。残り 50 ms を推論・送信・読み出し・割り込みの分とする）を超えたら
    stride 40 ms に落とす（約 100 ms の見込み。並びは保つ）。それでも超えたら、スペクトル重心を落とす段か IMU 14 次元だけで #24 を進めることになるが、
    どちらも次の項の記録を先に書く。基板の変更（docs/decisions/0001 の再検討条件）を含めてどれにするかは #28 で人が決める。
  - `docs/evaluation.md` 8 行目の特徴量の指定を変える経路（スペクトル重心を落とす段、IMU 14 次元だけにして音の特徴量をすべて外す経路）に進む場合は、
    評価の定義からの逸脱に当たる。進む前に `docs/decisions/` の記録（音の式の記録、またはその追記）に「`docs/evaluation.md` 8 行目の特徴量の指定を M2 について
    置き換える」と明記し、8 行目にその記録への参照を足すかどうかをその plan で決める（`docs/evaluation.md` の編集は Codex のレビューのゲートの対象）。
    記録なしにその経路へ進まない。この記録は 8 行目を変えていない。
  - 式を確定する場所: #21 の plan。#21 の plan は、`firmware/bench/` の案2 のパラメータを変えた実機の計測（合成信号、#17 と同じ条件）と、
    収集日1〜3 の中だけの交差検証（収集日ごと。0014 の手順のとおり、各 fold の `Standardizer` とモデルは fold の学習側だけで作る。収集日4 は見ない）で
    削った式の検出率・誤検出率が 0012 の式と比べて崩れていないことの確認（参考値。合格線の数字ではない）を含み、式・定数・次元の順序を新しい記録に書いてから
    EI に投入する。
- 特徴量ベクトルの次元数と順序はその記録が決める（IMU 14 ＋ 音 N。`FEATURE_NAMES` と同じ流儀で名前を付ける）。
- 正規化（平均と標準偏差による標準化。int8 の量子化で次元ごとの桁の違いを吸収するため）。統計量の母集団は 0014 と同じ考え方で、
  「その統計量を使って学習するモデルの fit に使うセッションの `valid` な窓の全部」とし、検証に使うセッションを含めない。
  - 収集日1〜3 の中の交差検証（式の選択）: 各 fold の学習側だけ（0014 の手順 4）。
  - EI での学習: EI の学習中に validation に回すセッションを除いた、fit に使うセッションだけ。収集日4 は含めない。
  - 装置・#22 の閾値の決定（収集日4）・#27: EI での学習に使った統計量をそのまま定数として使う。
  EI に投入するのは正規化後の値、装置は同じ定数で正規化してから推論する。定数は #22 でライブラリと一緒に `firmware/detector/` に置き、PC 側の再採点
  （#22・#23）も同じ定数を使う。定数を EI の側（Raw data ブロックのスケーリング等）に持たせる場合も、母集団は同じ（#21 の plan で決める）。
- 装置の出力は陽性・陰性の 2 値（`swallow` の確率が凍結した閾値以上なら陽性）。LED（docs/decisions/0018）はこの 2 値だけを受ける。
- #23 の DETECT / FEAT の形式を決めるときに守る要件（形式そのものは #23 が決める）: FEAT が運ぶ特徴量は装置が正規化する前の値（物理単位。PC 側で同じ定数を
  掛けて再採点できるようにするため）で、次元数と順序は音の式の記録に従い `meta.json` に残す。DETECT が運ぶ確率は `swallow` の確率で、`cough` の確率・クラスは
  載せない。

### 投入するデータ

- 収集日1〜4 の `self` の 28 セッション（M1 の記録。`data/raw/` の `split.split_sessions(data/raw, 14)` の `train` + `eval` と一致するもの）から、

  docs/decisions/0005）。

  項目名は `<セッション名>_<窓の開始 t_ms>`。メタデータにセッション名・収集日（フォルダ名の先頭 8 桁）・窓の開始 `t_ms` を付ける。

- 投入した項目の一覧（セッション名・窓の数・クラスごとの数）を投入スクリプトが標準出力に出し、#21 の log に貼る（EI 上のセッションごとの項目数と照合する）。
- 投入は API キーを環境変数で渡して行う。キーはコミットしない（docs/log/2026-09-20.md）。

### ラベルの規則（docs/decisions/0014 のまま）

- 嚥下のマーカー `s`（開始時刻 `t`）に対し、窓の中心 `w + 0.5` が `[t, t + 1.0]` に入る窓を `swallow`（陽性）。中心が `[t − 0.5, t)` か `(t + 1.0, t + 1.5]` に入る窓は
  投入しない（境目）。近接した 2 つの嚥下では、片方の陽性がもう片方の境目より優先される。
- どの嚥下の `[t − 0.5, t + 1.5]` にも中心が入らない窓が陰性。陰性は下の 3 クラスの規則で `cough` と `other` に分ける。
- これは学習のラベルだけの規則で、評価の数え方（`docs/evaluation.md`、docs/decisions/0011）は変えない。

### 3 クラスの線引き

- 学習のクラスは `swallow` / `cough` / `other` の 3 つ。#20 で `c` の窓と `s` の窓が 29 次元で線形に分かれる（fold の外の ROC-AUC 合算 0.902）ことが分かったため。
  減る誤検出は最大でも全体の約 2 割（咳に紐づく誤検出 37/178）で、これだけでは M2 の誤検出率の合格線（1 回/分）に届かない。
- `cough` の窓: 咳のマーカー `c`（開始時刻 `t_c`）に対し、中心が `[t_c, t_c + 1.0]` に入り、かつどの `s` の `[t − 0.5, t + 1.5]` にも中心が入らない窓
  （`s` の陽性と境目の規則が先に掛かる）。中心が `[t_c − 0.5, t_c)` か `(t_c + 1.0, t_c + 1.5]` に入る窓は投入しない（`s` と同じ形の境目）。
- `other` の窓: 陰性のうち `cough` でも `c` の境目でもない窓。`t`（発話）・`n`（首の動き）・`q`（静止）は別のクラスにしない。
- 装置の出力は 2 値。`cough` は陰性に畳む。`cough` の確率・クラスは DETECT・FEAT・LED・`docs/evaluation.md` の数え方のどこにも出さない。
  咳を「むせ」として出さない（CLAUDE.md「作らないもの」）。EI 上のクラス名・ラベル名にも `choke`・`むせ`・`aspiration`・`risk` に当たる語を使わない。
- EI の学習でクラスの不均衡（`other` が大半）をどう扱うかは #21 の plan で決める（`other` の間引きをする場合も、間引く単位はセッションの中の窓の一様な間引きに限り、
  セッションごと・収集日ごとに偏らせない）。

### 学習・検証の分け方（人の決定を EI の上で守る形）

- EI の training set = 収集日1〜3（21 セッション）、test set = 収集日4（7 セッション）。項目のメタデータの収集日で分け、投入スクリプトが振り分ける。
  分割はセッション単位で、窓単位の分割は EI の中でもしない。
- EI の学習中の validation 分割（早期終了、EON Tuner の探索、モデルの選択）は、窓のランダム分割にしない。メタデータ（セッション名または収集日）で分ける。
  EI がメタデータによる分割をできない場合は #21 の plan で止まって報告する（validation を無しにできるならそれでもよい）。
- 閾値は #22 が収集日4（test set）だけで決めて凍結する。決め方は 0014 と同じ形で、誤検出率の条件は M2 の合格線 1 回/分。
- 収集日4 の数字を見た後は、モデルもハイパーパラメータも特徴量の式も変えない。全 4 日で学習し直さない。
- 特徴量の式（M2 の音の式）の選択と、EI のモデル・ハイパーパラメータの探索は、収集日1〜3 の中だけで行う。
- M2 の合格線の数字は #27 の新しい記録（`meal`）で出す。EI の test set の窓単位の数字も、#22 のイベント単位の数字も、参考値と明記する。

### C++ ライブラリのコミットの扱い（`model_metadata.h` のプロジェクト ID と所有者名）

- #22 の書き出し（C++ library、int8）は zip の中身をそのまま `firmware/detector/` の下に展開してコミットする。`model-parameters/model_metadata.h` の
  `EI_CLASSIFIER_PROJECT_ID`・`EI_CLASSIFIER_PROJECT_OWNER`・`EI_CLASSIFIER_PROJECT_NAME` は書き換えない。
  理由: プロジェクトを Public にするので ID と名前は公開情報になる。所有者名は開発者の EI アカウントの表示名で、`p1` に関わる情報ではない。
  API キーは書き出しに含まれない（#17 の書き出しで確認）。
- コミットの前に、`model_metadata.h` の所有者名と、書き出しに含まれる文字列に線引きを越える情報が無いことを人が目視で確かめる。zip の sha256、EI の版、
  `EI_CLASSIFIER_PROJECT_DEPLOY_VERSION` を #22 の log に書く。
- プロジェクトを Private にする決定になった場合は、3 つの define の値を書き換えて（ID は 0、所有者名とプロジェクト名は空文字列）コミットし、書き換えたことと
  元の zip の sha256 を log に書く。3 つの define は `edge-impulse-sdk/` から参照されていない（#17 の書き出しで確認）ので、ビルドは変わらない見込み（#22 で確認）。
- `firmware/bench/.gitignore` の `src/`（ダミー impulse の書き出し）は今のまま無視する。ダミーは本番の impulse ではなく、コミットする理由が無い。

## 理由

- **特徴量ベクトルを投入する形だけが、EI の「同じサンプリング周波数」の制約に掛からずに IMU と音の結合を学習できる。** 16 kHz の音声と 104 Hz の IMU を
  1 つの時系列にはできない（docs/log/2026-09-20.md）。特徴量ベクトルは窓ごとの 1 サンプルなので周波数の問題が無い。
- **片方ずつのモデルを規則で結合する案（2・4）は、結合の重みを学習しない。** #20 の 4 fold で、両方の ROC-AUC（0.851〜0.947）は IMU のみ（0.793〜0.911）・
  音のみ（0.754〜0.794）より 4 日とも高く、M1 の評価側でも片方だけでは合格線に届かなかった（IMU のみ 0.464、音のみ 0.435、両方 0.783）。
  音は `saliva`、IMU は `water` を拾う（役割が分かれる）ので、結合は要る。
- **0012 の音の式のままでは RP2040 に載らない。** #17 案2 の 1099 ms は 250 ms の 4.4 倍で、FFT が 82%。EI の DSP（案1）でも 559〜735 ms。
  見立て（実測ではない）で収まる方向は stride と FFT の回数を減らすことだけで、これは 0012 の式の変更に当たる。0012「M2 との関係」のとおり、
  新しい記録を足してから変える。
- **式は実測してから固定する。** 0012 は「実データを見る前に固定する」ためのものだった。M2 の式は「装置で測る前に固定する」と、見立てが外れたときに
  二度変えることになる。#21 の plan で、実機の計測と収集日1〜3 の中の確認を通してから固定する。収集日4 は閾値のために取っておく。
- **3 クラスは費用が小さく、線形に分かれることが分かっている。** 効き目は最大 2 割で、それ以上を期待しない。装置の出力を 2 値に畳むので、LED・DETECT・評価は
  2 クラスの場合と同じ形になり、#19・#23・#24 の決定を変えない。
- **Public にする。** 投入するのは `self` の特徴量ベクトルだけで、生の音声も上げない。企画の公開（M5）で EI のプロジェクトを示せる。条件を先に書いておき、
  切り替えは条件の確認と同時に行う。`p1` のデータは入れない。
- **書き出しはそのままコミットする。** 書き換えた書き出しは、EI の版との対応を取りにくい。ID と名前は Public なら公開情報で、所有者名は開発者のもの。
  API キーは含まれない。

## 選ばなかった案

- **候補 1（PC 側で計算した特徴量を投入。装置側は未定）。** 投入の形は採用した方式と同じだが、装置側の計算を決めていない。EI の DSP は 0012 の式を作れないので、
  装置側を決めると採用した方式になる。
- **候補 2（音声だけ EI で学習、IMU は装置の規則）。** 音のみは日をまたぐと最も弱い（検出率 0.070〜0.594）。IMU の規則は学習されず、結合の重みも学習されない。
  EI の MFCC / MFE のスライス版でも 559〜735 ms で 250 ms に収まらない。
- **候補 3（カスタム処理ブロック）。** Studio 側の Python と装置側の C++ の二重実装になる。同じ周波数の制約はデータ項目に掛かるので、音声と IMU を
  1 項目に入れるには結局 PC 側でそろえる必要がある。採用した方式に対して工数が増えるだけで、利点が無い。
- **候補 4（複数 impulse）。** 音声 impulse の DSP が案1 と同じ時間で収まらない。2 つのモデルの出力を規則で結合するので結合の重みを学習しない。
  #21・#22 の工程が 2 倍になる。複数 impulse の書き出しはこの環境では未確認。
- **候補 5 のまま（0012 の 29 次元を装置で計算）。** RP2040 では 1107 ms で不成立。基板を FPU 付きに替える案（docs/decisions/0001 の再検討条件）は
  #28 で人が決める。#18 では選択肢として残すだけ。
- **IMU のみ（音を使わない）。** 8.1 ms で時間は収まるが、検出率は 0.419〜0.625（M1 の評価側 0.464）で 85% から遠い。削った式が実機で収まらないときの退避先。
  進む場合は音の特徴量をすべて外すので、`docs/evaluation.md` 8 行目の特徴量の指定を M2 について置き換える記録を先に書く（「方式」の項）。
- **ホップを 250 ms より長くする、音の特徴量を 2 ホップに 1 回だけ更新する。** `docs/evaluation.md` の窓（1.0 秒 / 0.25 秒）を変えることになる。
- **#18 で削った式まで決め切る。** 実測なしに固定すると、外れたときに式の記録を 2 回書く。方向と梯子だけをここで決め、式は #21 の plan で実測してから固定する。
- **2 クラスのまま。** 費用は小さいが効き目も最大 2 割で、どちらでも合格線には別の手が要る。3 クラスにしても装置側は同じ形なので、線形に分かれる分は取りに行く。
- **`t`・`n` も別のクラスにする（5 クラス）。** #20 は `c` しか見ていない。分かれる根拠が無い。
- **M2 の間 Private のまま。** 条件を満たしていれば Public にしない理由が無い。ただし M5 まで Private にしておき、記事の公開と同時に切り替える運用も可能
  （その場合はこの記録に追記する）。
- **書き出しの ID・所有者名を消してコミットする。** Public なら消す理由が無い。Private の場合の扱いとして残す。
- **書き出しをコミットしない。** 人の決定（C++ ライブラリはコミットする）に反し、#24 のビルドの再現ができない。
