# 0018 一口ボタンは M2 で使わず、LED は緑・黄の2色を「目安」として点ける

日付: 2026-09-24　状態: 採用

人が 9/24 に決めた方向（一口ボタンは M2 で使わない、LED は緑・黄のみ、赤は出さない、むせの分類は作らない）と、
その上で人が決めた数値と文言（基板の RGB LED、最初の陽性窓で点ける、保持 2.0 秒、1.0 秒で消灯）をここに固定する。
`docs/evaluation.md` の定義と合格線は変えていない。採否の経緯は Issue #19 のコメントにある。
点灯の条件を案A のままにするかは、#20 の集計値で確かめる（「#20 で確かめる箇所」）。

## 決定

### 一口ボタン

- M2 では一口ボタン（マーカー `b`）を使わない。嚥下イベントの時刻と回数はボタンなしで取る。
- 潜時（口に入れてから嚥下開始までの秒数）は一口の時刻が要るので、M3 以降で扱う。M3 の本人試用で `b` を打つかどうかは、
  M3 の前に別に決める（`docs/plan.md`「M3 の前に行うこと」と同じ時期）。
- `docs/data-schema.md` の `events.csv` の `b` は残す（形式は変えない）。`tools/record.py` のキーも変えない。
  #26 の `meal` の手順では `b` を打たない。
- 検出器ファームウェアにボタン入力を付けない。装置の入力はセンサだけ。

### LED の色と条件（M2）

窓は `docs/evaluation.md` の 1.0 秒 / ホップ 0.25 秒。「陽性」は装置の2値の出力（#18 の方式、#22 で凍結した閾値）。
LED は窓の結果が出るたび（0.25 秒ごと）に更新する。

| 表示 | 意味（介助者向け） | 条件 |
|---|---|---|
| 緑 | 嚥下を確認した目安 | 現在の窓（開始 `w`）を含めて、開始が `[w − 1.75, w]` にある陽性の窓が1つ以上ある（窓の開始時刻の差で数える） |
| 黄 | 嚥下をまだ確認していない目安 | 装置が動いていて、緑の条件を満たさない |
| 消灯 | 動作していない | 起動から最初の窓の結果が出るまで。センサの初期化に失敗したとき。新しい窓の結果が 1.0 秒（4 ホップ分）以上出ないとき（窓の結果とは別に `millis()` で測る） |

- **緑を点ける時点**: 最初の陽性窓が出た直後（案A）。陽性の連続の終わりを待たない。
- **緑を保つ時間**: 最後の陽性窓の開始 `w_p` から、開始が `w_p + 1.75` 以下の窓まで緑、開始が `w_p + 2.0` の窓から黄。
  ホップ 0.25 秒なら緑は結果 8 回分 = 2.0 秒。陽性窓が続けば延びる（陽性のたびに `w_p` を取り直す）。
  k 窓の連続なら、緑は `(k − 1) × 0.25 + 2.0` 秒。
- **黄に戻る条件**: 開始が `[w − 1.75, w]` にある陽性の窓が無い。
- 条件を窓の番号（直近 8 窓）ではなく開始時刻の差で書くのは、窓の飛び（取りこぼし）があっても装置の状態と PC 側の再計算が同じ式で
  一致するため。装置は `w_p` を保持して現在の窓の開始と比べるだけで、窓の履歴を持たない。
- **赤は出さない。** 黄は時間が経っても色を変えない（「未嚥下が続く」の段階付けは赤の役割で、M3 以降）。
  咳・むせを表す表示は無い（装置の出力は2値で、咳は陰性に畳む。#18）。
- **緑と黄は常時点灯。** 点滅、明るさの段階、回数の表示、音は使わない。
- 起動失敗の表示は記録ファームウェアと同じ `LED_BUILTIN`（D13、RGB とは別の LED）の 200 ms 点滅。RGB は消灯のまま。
- **LED は評価に関わらない。** M2 の検出評価は `detect.csv` の `positive` だけを `docs/evaluation.md` のとおり数える。緑の保持
  （1.75 秒）は評価の「陽性が連続する窓」の数え方（docs/decisions/0011 の 0.375 秒）とは別物で、評価の数え方を変えない。
- **DETECT の `led` の値**: `0` 消灯、`1` 黄、`2` 緑。#23 が `docs/data-schema.md` に書くときにこの値を使う。
  `positive` と `window_t_ms` の列から上の規則で `led` を PC 側で再計算でき、装置の `led` 列と一致することを #25 で確かめる。
  一致の確認は結果が届いた行（`detect.csv` の各行）に限る。消灯の時点は行として残らない。

嚥下の開始から緑までの遅れ: 陽性になる窓の終端（検出の定義では窓の中心が `[t − 0.5, t + 1.5]` なので、終端は開始から
0〜2.0 秒）＋ 1 ホップ分の処理（#24 の上限 250 ms）。実際の値は #25 で `events.csv` の `s` と `detect.csv` の `led` から出す。

### 装置の LED

- **基板の RGB LED（NINA-W102 経由）を使う。** WiFiNINA ライブラリが要る（`CMakeLists.txt` の `deps` に
  `arduino-cli lib install WiFiNINA` を足す。#25）。`NinaPin` 版の `pinMode` / `digitalWrite` は `firmware/detector/` の
  LED モジュールの内側だけで呼ぶ（docs/decisions/0001）。「開始が `[w − 1.75, w]` にある陽性窓があるか」の規則は Arduino に
  依存しない関数に分け、PC 側の再計算と同じ式にする。1.0 秒の消灯は窓の結果とは独立した `millis()` のタイムアウトで実装する。
- 黄は赤＋緑の同時点灯。見え方（緑と区別が付くか）と極性は #25 で実機で確かめる。
- **外付けに切り替える条件**（どれか1つで切り替える。規則と文言は同じ）:
  (a) バンドやケースで隠れて、介助者側から見えない。
  (b) NINA への書き込みで `t_ms` の飛びが作業上の基準（1%、#7）を超える、または 1 ホップの処理が 250 ms に収まらなくなる。
  (c) WiFiNINA を入れたビルドが通らない、または NINA のファームウェアの版で動かない。
  切り替え先は RP2040 の GPIO に直結した緑・黄の 2 灯（抵抗付き。M2 は2色なので3色は要らない）。

### 文言

対象は、装置に貼る表示、介助者に渡すカード、`docs/`（`firmware/detector/README.md` を含む）、log、Issue、コードの名前。

装置に貼る表示（ケースの介助者側。本人の正面から見えにくい向きに貼る）:

```
嚥下の目安（判定ではありません）
緑: 嚥下を確認した目安（約 2 秒）
黄: まだ確認していない目安
```

介助者に渡すカード:

```
この光は嚥下の目安です。判定や指示ではありません。
緑: 喉の動きと音から嚥下らしいと見た目安。約 2 秒で黄に戻ります。
黄: まだ確認していない目安。時間が経っても色は変わりません。
消灯: 動いていません。
次の一口をいつにするかは、介助者が決めます。
咳や首の動きの直後に緑が点くことがあります。
誤嚥（気管に入ること）が起きたかどうかは、この装置では分かりません。
```

書き方の決まり:

- 「目安」を使う。装置を主語にした「判定」「判断」「指示」「合図」「許可」「警告」「注意」と、「安全」「危険」「正常」「異常」
  「OK」「NG」「進んでよい」「止めて」は使わない。「判定ではない」のような否定は可。
- 表示は介助者に向けて書く。本人に「見てください」「待ってください」と言わない。
- 「誤嚥」の語は、装置に貼る表示には入れない。カードと文書では「分からない」という否定の形でだけ使う。
  「誤嚥検出」「aspiration」「risk」に当たる語は、文書・コード・ラベルのどこにも入れない（CLAUDE.md「作らないもの」）。
- コードの名前は色と状態で付ける（`LED_OFF` / `LED_YELLOW` / `LED_GREEN`、`led_hold_windows` など）。
  `alert` / `alarm` / `warn` / `risk` / `verdict` / `safe` / `unsafe` / `judge` に当たる名前を使わない。

## 理由

- **ボタンを使わない。** 企画書 12章の対策どおり、検出と回数はボタンなしで取れる設計にし、潜時だけをボタン依存にする。
  M2 の合格線（検出率、誤検出率）は `docs/evaluation.md` のとおり `s` と非嚥下区間だけで決まり、`b` を使わない。
  M2 の通し記録（#27）は開発者が1人で行うので、ボタンを足すと記録の手が1つ増えるだけで数字は変わらない。
- **緑は最初の陽性窓で点ける（案A）。** 介助者が食事中に見る表示なので、遅れが最も小さい条件を採る。連続の終わりを待つ案は
  最低 0.25 秒、M1 の評価側の最長の塊（7 窓）では 1.75 秒遅れる。M1 の評価側では塊の 46% が 1 窓だけなので、連続の終わりを
  待っても得られる情報は少ない。塊の長さと誤検出の関係はまだ集計していない（#20 で集計する）。
- **保持は 2.0 秒。** 1 窓だけの塊（46%）は保持が無いと 0.25 秒しか点かず、目で追えない。2.0 秒は `docs/evaluation.md` の
  嚥下の区間 `[t − 0.5, t + 1.5]` の長さと同じで、1回の嚥下の陽性窓がこの中に収まる。M1 の記録手順の嚥下の間隔（10 秒以上）より
  十分に短く、次の嚥下の前に黄へ戻る。食事の一口の間隔は M2 の `meal` の記録（#27）で初めて分かる。
- **黄は変化させない。** 「未嚥下が続く」を段階で示すのは赤の役割であり、時間の閾値を置くと「そろそろ次へ」という指示に読める。
  M2 の LED は「確認したか、まだか」だけを示す。
- **消灯の規則を置く。** 窓の結果が止まったときに最後の色が残ると、動いていない装置の緑を介助者が信じてしまう。
  1.0 秒（4 ホップ）で消灯にすれば、止まったことが表示で分かる。止まっている間は窓の結果が来ないので、この監視は窓の結果とは
  別の時計（`millis()`）で動かす。
- **基板の RGB LED を使う。** 追加の部品と配線が要らず、M2 の期間（2 週間）に収まる。喉元の基板の LED は本人からは見えず、
  向かい合う介助者からは見えるので、企画書 10章「表示は介助者側に向ける」と合う。NINA 経由の書き込みのコストは未確認なので、
  切り替える条件を先に書いておく。
- **文言は否定を1つ入れる。** 「目安」だけでは装置が何をしないかが伝わらない。企画書 12章の「装置の表示にも『目安』と明記」に加え、
  「判定ではありません」を表示に、「誤嚥は分からない」をカードに置く。

## #20 で確かめる箇所

- 点灯の条件を案A（最初の陽性窓）のままにするか、案C（陽性窓が2つ連続したとき）にするか。#20 が出す「塊の長さ別の誤検出の割合」
  （人の決定で #20 に足した）と「咳の開始から何秒後に誤検出が起きるか」を見て、1 窓だけの塊の大半が誤検出なら案C を候補にする
  （遅れは 0.25 秒増える）。そうでなければ案A のまま。
- #20 の塊の集計は探索的な参考解析で、既に数字を見た M1 の評価側（収集日3+4）を含む。この集計で表示規則を決め切らない。
  案C に変えるかどうかの最終確認は、#25 の実機の記録（M1 の 28 セッションとは別の、新しいセッション）で LED の遅れと誤表示を
  見て行う。
- M2 の検出評価（#27）は `positive` だけを使う。案A でも案C でも評価の数字は変わらない。
- 保持 2.0 秒と消灯 1.0 秒は決定で、#20 では動かさない。
- 案C に変えるときは、#25 の plan（Codex のレビューを通す）でこの記録に「追記」の節を足す。番号は変えない。

## 選ばなかった案

- **M2 でも一口ボタンを使う。** 潜時が M2 で出せるが、合格線に関係なく、記録の負担が増える。企画書 12章の対策に反する。
- **赤を出す／3段階にする。** 「むせ」は咳の分類が要り、M2 では作らない（人の決定、#18）。「未嚥下が続く」の段階付けは時間の閾値が
  指示に読める。M3 以降で、本人の記録を見てから決める。
- **陽性の連続の終わりで点ける（案B）。** 遅れが増え、得られる情報が少ない（上の理由）。
- **陽性窓が2つ連続したときに点ける（案C）。** 今の集計では 1 窓の塊が誤検出に偏っているかが分からず、遅れが 0.25 秒増える分の
  根拠が無い。#20 の集計で偏りが出たときの切り替え先として残す（「#20 で確かめる箇所」）。
- **保持 1.0 秒。** 1 窓の塊で 1.0 秒しか点かず、目で追えないことがある。**保持 3.0 秒以上。** 近接した嚥下（水の記録では 10 秒以上
  あけるが、食事では未知）が1つの緑に見え、黄に戻るのが遅れる。
- **消灯の規則を置かない（最後の色を残す）。** 窓の結果が止まったときに緑が残り、動いていない装置の表示を介助者が信じてしまう。
- **黄を「未確認・待つ」と書く。** 企画書 5章の語だが、「待つ」は介助者への指示に読める余地がある。「まだ確認していない目安」にした。
- **カードに「誤嚥は分からない」を書かない。** 「目安」だけでは装置が何をしないかが伝わらず、緑を安心と読まれる。装置に貼る表示には
  入れず（短く保つ）、カードにだけ否定の形で書く。
- **点滅・明るさの段階・確率の表示。** 点滅は急かす合図に見える（企画書 10章）。確率を明るさで出すのは「スコア」に読める
  （CLAUDE.md「risk score に相当する表現」）。回数は `detect.csv` に残るので、表示しない。
- **ブザー・音。** 食卓で本人にも聞こえ、急かす道具になる。
- **黄を時間で変える（例: 30 秒で点滅）。** 赤の役割で、M3 以降。
- **外付けの3色 LED。** 配線と部品が要り、M2 の期間に収めるための余裕が減る。基板の LED が使えない場合の切り替え先として
  2 灯の形で残す。
- **`LED_BUILTIN` だけで表す。** 1色しか無く、緑と黄を分けられない。起動失敗の点滅にだけ使う。
- **RGB LED を WiFiNINA なしで直接駆動する。** コアが `NinaPin` の `pinMode` / `digitalWrite` をエラーにするので不可。

## 実装に渡すこと

- #23: DETECT の `led` は `0` 消灯 / `1` 黄 / `2` 緑。`analysis/evaluate_detector.py` は `led` を評価に使わない。
- #25: 上の表の規則。WiFiNINA を `deps` に足す。LED モジュールの境界。「開始が `[w − 1.75, w]` にある陽性窓があるか」の規則を
  Arduino に依存しない関数にし、`positive` と `window_t_ms` からの再計算と `led` 列の一致を確かめる。一致の確認は結果が届いた行に限る。
  1.0 秒の消灯は窓の結果とは独立した `millis()` のタイムアウトで実装し、止めたとき（センサを止める、USB を抜かずに推論を止める、など）に
  消灯することは実機で確かめる（`detect.csv` には残らない）。極性、黄の見え方、1 回の書き込みの時間、`t_ms` の飛びを実機で確かめて
  log に書く。表示とカードの文面をそのまま `firmware/detector/README.md` に載せる。開発者が装着したまま目で確かめるには鏡かカメラが要る。
- #26: `meal` の手順に「`b` は打たない」と書く。`docs/recording-protocol.md` 68 行目の「（一口ボタンの扱いは保留中の判断）」を
  この記録への参照に直す。

## 確かめていないこと

- `digitalWrite(NinaPin)` 1 回の時間と、PDM・IMU の取り込みへの影響（#25 で実測）。
- RGB LED の極性と、赤＋緑が黄に見えるか（#25）。
- 喉元に付けた基板の LED が、25 mm のバンドとケースで隠れないか（#25 で人が確かめる。隠れるなら外付け 2 灯へ）。
- 食事の一口の間隔と、2.0 秒の保持が食事で長すぎないか（#27 の `meal` の記録で初めて分かる）。
