# 0014 M1 の学習と評価の手順を、実データを見る前に固定する

日付: 2026-09-20　状態: 採用

M1 の分岐点の数字（#13）を出す手順を、`analysis/train_eval.py` とそのテスト（`analysis/test_train_eval.py`）で固定した。
`docs/evaluation.md` の定義と合格線、`docs/data-schema.md`、特徴量の式（docs/decisions/0012）、評価の数え方
（docs/decisions/0011）は変えていない。`analysis/evaluate.py`・`analysis/split.py`・`analysis/features.py` も変えていない。
下の「決定」は人が決めた。採否の経緯は Issue #13 のコメントにある。

## 決定

- **学習のラベル。** 嚥下のマーカー `t`（`events.csv` の `s`。開始時刻）に対して、窓の中心 `w + 0.5` が `[t, t + 1.0]` に
  入る窓を陽性とする。中心が `[t − 0.5, t)` か `(t + 1.0, t + 1.5]` に入る窓は、陽性にも陰性にもせず、学習に使わない
  （嚥下をほとんど含まない窓を陽性と教えない）。どの嚥下の `[t − 0.5, t + 1.5]` にも中心が入らない窓が陰性。
  近接した2つの嚥下では、片方の陽性がもう片方の「使わない」より優先される。これは学習のラベルだけの規則で、
  評価の数え方は変えない。
- **閾値。** 学習側のセッションだけで決める。学習側の中の交差検証で、候補 0.05, 0.10, …, 0.95 のそれぞれを、評価と同じ
  数え方（`event_metrics` → `aggregate` と同じ合算）で採点する。誤検出率が 3.0 回/分以下の候補のうち、検出率が最大のもの。
  同率なら高いほう。満たす候補が無ければ、誤検出率が最小のもの（同率なら高いほう）。
- **正規化。** 統計量（平均と標準偏差）は、学習に使うセッションの `valid` な窓を全部使って作る。学習に「使わない」とした
  境目の窓も正規化には入れ、分類器の fit だけから外す（`features.Standardizer` の API のまま。装置が実際に見る窓の分布に近い）。
- **評価側の保護。** 既定の実行は学習側だけを使い、交差検証の数字を出す。評価側のセッションの `imu.csv`・`audio.wav`・
  `audio_chunks.csv`・`events.csv` は開かない（`meta.json` だけは、`split_sessions` が分割の前に全セッションの subject を
  検査するために読む）。`--final` を付けたときだけ評価側を採点する。
- 常時陽性の場合の数字と、陽性窓の割合を、参考値として報告に並べる（#10 で決定済み。docs/decisions/0011「既知の弱点」）。

## 手順（`analysis/train_eval.py`）

`python analysis/train_eval.py <root> --eval-min <N> [--final]`

1. **分割**: `split_sessions(root, eval_min, subject="self")`。`--eval-min` は必須の引数（最後の2収集日のセッション数。
   `docs/recording-protocol.md`）。分割の直後に、フォルダ名の日付（先頭 8 桁）で次を検査し、外れたら止まる:
   評価側の収集日がちょうど 2 日、学習側の収集日が 1 日以上、学習側のどの収集日も評価側のどの収集日より前。
   subject は `self` 固定（`docs/evaluation.md`「M1・M2 の数字は `self` のみ」）。
2. **特徴量**: `features.extract_session`。`valid = False` の窓は、学習・正規化・交差検証の学習に使わない。採点
   （交差検証の検証側と、評価側）では陰性として扱い、陽性にしない。その数を報告に出す（下の「無効な窓の効果」）。
3. **モデル**: 正規化は `features.Standardizer`（学習に使うセッションだけで `fit`）。分類器は scikit-learn の
   `LogisticRegression(C=1.0, class_weight="balanced", max_iter=1000)`。ハイパーパラメータは固定で、探索しない。
   乱数は使わない（`lbfgs`、決定的）。
4. **交差検証（学習側だけ）**: 学習側の収集日が 2 日以上なら収集日ごと（1日を検証側に回す）、1 日なら1セッションごと。
   各 fold で、`Standardizer` とモデルを fold の学習側だけで作り、検証側のセッションの全窓に確率を付ける。全 fold の確率を
   集め、閾値の候補ごとに、セッション単位で `event_metrics`（`t0_s` と `duration_s` は `evaluate.session_span`、嚥下は
   `evaluate.load_events`、陽性窓は確率が閾値以上で `valid` な窓の `t_start_s`）を計算し、回数を合算して検出率と誤検出率を
   出す。合算の式は `evaluate.aggregate` と同じ。交差検証では 3 セッション未満でも止めないよう、合算だけの関数を
   `train_eval.py` の中に置く（#10 で固定した `evaluate.py` には足さない）。上の基準で閾値を決める。
5. **最終モデル**: 学習側の全セッションで `Standardizer` とモデルを作り直す。
6. **評価（`--final` のときだけ）**: 評価側のセッションごとに `event_metrics` を計算し、`split_sessions` が返した `eval` の
   一覧をそのままキーにして `evaluate.aggregate` に渡す（docs/decisions/0011「塞がっていない経路」への対応。辞書のキーが
   `eval` の一覧と一致することを実行時に確かめる）。
7. **参考値**: 評価側で、全窓を陽性にした場合の検出率と誤検出率、モデルの陽性窓の割合（陽性窓 ÷ 全窓）。学習側の
   交差検証でも同じ2つ。
8. **報告**: 標準出力に Markdown で出す。ファイルは書かない（モデル、特徴量、確率を保存しない）。中身は、実行の条件
   （`--eval-min`、コミットのハッシュ、scikit-learn と numpy の版）、学習に使ったセッションの一覧、評価に使ったセッションの
   一覧、閾値とその決め方・候補ごとの交差検証の表、無効な窓の数、（`--final` のとき）セッションごとの表（cond、嚥下、検出、
   誤検出、非嚥下の分数）、合算の検出率と誤検出率、イベント単位の混同行列（TP / FN / FP。TN は出さない）、参考値、
   合格線との比較。既定の実行では、評価側の一覧はセッション名だけを出し、「評価側は採点していない」と明記する。
   波形、特徴量の値、個々の窓の確率は出さない。

## 止まる条件

次のどれかに当たるときは、fold と該当のセッション名を示して止まる。fold を黙って飛ばさない。評価側のセッションで補わない。

- 分割の検査（手順 1）に外れる。
- 交差検証のグループ（収集日、または1日だけのときはセッション）が 2 つ未満。
- ある fold の学習側で、`valid` かつラベルの付いた（陽性か陰性の）窓に、陽性と陰性の両方がそろっていない。
  最終モデルでも同じ。
- 交差検証の合算で、嚥下が 0 件（検出率が出ない）、または非嚥下の時間が 0（誤検出率が出ない）。

fold の検証側に嚥下が無い（`quiet` だけ、など）のは止めない（`event_metrics` は嚥下 0 件のセッションを扱える）。
学習側のどのセッションにも嚥下が無い場合は、合算の検査より先に「陽性と陰性がそろっていない」で止まる。

## 無効な窓の効果

無効な窓（`valid = False`）は採点で陽性にしない。非嚥下の区間で陽性が続いている途中に無効な窓を挟むと、陽性の窓の
開始時刻の差が 0.5 秒以上になり、`evaluate.py` の連続の判定（`HOP_S * 1.5` = 0.375 秒以下）を超える。1つの陽性の連続が
2つの塊に分かれ、誤検出の回数が増える場合がある。厳しい側に出る。数え方は変えない。テストで期待値として固定してある
（陽性が続く 9 窓の途中の 2 窓が無効なら、誤検出は 1 回ではなく 2 回）。

## 理由

- **実データを見る前に固定し、結果を見てから動かさない。** 記録（#12）は人が数日かけて行う。データがそろう前に、学習の
  ラベル、閾値の基準と候補、モデルの設定、交差検証の単位、止まる条件、正規化の扱い、報告に出すものを、スクリプトとテストで
  固定した。結果を見てからやり方を動かす余地を残さない（docs/decisions/0003、0011 と同じ理由）。
- **閾値を学習側だけで決める。** 評価側の数字を見て閾値を選ぶと、評価側が学習に混ざる。既定の実行が評価側のファイルを
  開かないので、閾値を確かめるために何度実行しても、評価側の数字は見えない。
- **学習のラベルを評価の区間より狭くする。** 評価の区間 `[t − 0.5, t + 1.5]` の端の窓は、嚥下をほとんど含まない。それを
  陽性と教えない。陰性とも教えない（境目）。
- **ハイパーパラメータを探索しない。** M1 は「手作り特徴量＋ロジスティック回帰で足りるか」を見る分岐点で、探索の余地を
  増やすと、結果を見てから動かせる箇所が増える。

## 再現の条件

同じ入力に対して報告が一字一句同じになるのは、同じコミット、同じ依存の版（scikit-learn、numpy）、同じ実行環境で
実行したときまで（`lbfgs` は乱数を使わない）。scikit-learn・numpy・BLAS・実行環境をまたいだ一致は保証しない。
報告の「実行の条件」に出すコミットのハッシュと版が、再現の条件。この手順を固定したときの版は scikit-learn 1.9.1。
追跡しているファイルに未コミットの変更があるとき（または git が使えないとき）は、報告のコミットに `-dirty` を付ける。
`--final` は、その状態では採点せずに止まる（評価側の数字は、コミットから再現できる状態でだけ出す）。既定の実行は止めない。
`data/raw/` は無視されているので、この検査には掛からない。

## 実データでの実行（#12 のデータがそろってから。この手順は変えない）

1. `docs/recording-protocol.md` のとおり `data/raw/` を整理し、`python analysis/split.py data/raw --eval-min <N>` の出力を
   セッション名の一覧と照合する。
2. `python analysis/train_eval.py data/raw --eval-min <N>`（既定。学習側だけ）で、交差検証の数字と閾値を確かめる。
   何度実行してもよい。
3. `python analysis/train_eval.py data/raw --eval-min <N> --final` を実行し、出力をそのまま `docs/log/` に貼る。
   合格線に届かなくても、定義・分割・特徴量・閾値の決め方を動かさない。数字をそのまま報告する（Issue #13）。
   `--final` を実行した後は、評価側を動かさない（`docs/recording-protocol.md`）。
4. `self` なので、セッション名の日付はそのまま書いてよい。生データはコミットしない。

## 塞がっていない経路

- セッションのフォルダの中のファイル（`imu.csv`、`audio.wav`、`audio_chunks.csv`、`events.csv`）をシンボリックリンクや
  ハードリンクにする、または別名のフォルダにコピーすると、評価側のセッションの中身を学習側の名前で読ませられる。交差検証でも、
  同じ実体を2つのセッション名で置けば、検証側が学習に混ざる。`analysis/split.py` が拒むのは、セッションのフォルダ自体の
  リンクだけ。
- 通すには、`data/raw/` の中でわざとリンクやコピーを作る必要がある。入力ミスでは通らない（`tools/record.py` は、セッションごとに
  新しいフォルダへ実ファイルを書く）。コピーは inode の検査でも防げない。コミット前のレビュー（#13 のコメント）の指摘で、
  人の判断で CONCERN とした。コードでは塞がず、運用で注意する（`data/raw/` には `tools/record.py` が書いたフォルダだけを置く。
  `docs/recording-protocol.md`）。docs/decisions/0007・0011 の「塞がっていない経路」と同じ扱い。
