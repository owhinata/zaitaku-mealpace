# 0013 音声チャンクの `t_ms` の意味を、実装に合わせて文書に固定する

日付: 2026-09-20　状態: 採用

`docs/data-schema.md` の `audio.wav` の節の一文を変えた（#15）。ファイル名・列・単位・WAV の形式・フレーム形式は
変えていない。`docs/evaluation.md` の定義と合格線も変えていない。どちらに合わせるかは人が決めた。
採否の経緯は Issue #15 のコメントにある。

## 決定

- **文書を実装に合わせる。** `firmware/logger/logger.ino` は変えない。
- 音声チャンクの `t_ms` は、装置が PDM の受信コールバック（`on_pdm()`）でそのチャンクを読み出した直後に取った
  `millis()`。論理上はチャンクの終端側の時刻として扱う。
- 先頭サンプルの時刻の推定値は `t_ms − 1000 × チャンクのサンプル数 ÷ audio_hz` ms（64 サンプル・16 kHz なら 4 ms 前）。
- 「最後のサンプルの直後の時刻」とは書かない。コールバックの開始待ち、読み出しの時間、`millis()` の 1 ms の刻み、
  PDM のフィルタの遅れを含むので、そこまでは保証できない。
- **この換算は、コードから定めた論理上の時刻。** 下の叩きの実測は粗い整合の確認で、約 4 ms を実測で証明したものではない。
- `audio_chunks.csv` の列（`t_ms, sample_index`）と `audio.wav` の形式は変えない。
- **記録済みのセッションの変換スクリプトは要らない。** 旧いセッションも新しいセッションも CSV と WAV のバイト列は同じで、
  値は変わらず、読み方だけが変わる。読む側の全部（今は `analysis/features.py` だけ）が新しい読み方を使う。
  `data/sample/` の見本も `data/README.md` の記述（`t_ms` は元のまま）も変えない。

### 読む側の計算（`analysis/features.py`。docs/decisions/0012 の該当の段落を置き換える）

- チャンクごとの長さ `L[i] = sample_index[i+1] − sample_index[i]`。最終行は `L[last] = WAV のサンプル数 − sample_index[last]`。
- 先頭サンプルの時刻のアンカー `anchor[i] = (t_ms[i] − 1000 × L[i] ÷ audio_hz + AUDIO_CHUNK_T_OFFSET_MS) ÷ 1000` 秒。
  サンプルの時刻は、アンカーの間を線形補間し、最後のアンカー以後は 16 kHz の傾きで補外する（0012 のまま）。
- `AUDIO_CHUNK_T_OFFSET_MS` は 0.0 のまま残す。意味は「上の換算のあとに足す補正（系統的なずれが分かったとき用）」。
- 音声の飛びの判定は、生の `t_ms` の差分ではなく、換算後の時刻から出す。前のチャンクの推定の終端
  `end[i] = anchor[i] + L[i] ÷ audio_hz` と、次のチャンクの推定の先頭 `anchor[i+1]` の間の空白が、最頻のチャンク長から出す
  周期の `GAP_RATIO − 1` = 0.5 倍（64 サンプルなら 2 ms）以上なら飛びとし、飛びの区間は `(end[i], anchor[i+1])`。
  チャンク長が一定のときは、これまでの基準（`t_ms` の差分が周期の 1.5 倍以上。`tools/check_session.py` と同じ）と同じ判定になる。
  長さの違う正常なチャンク（32 / 96 サンプル）は空白が 0 で、飛びにならない。
- 入力の検証（最終チャンクの長さが 1 以上、最頻のチャンク長以下）、IMU の飛びの判定、特徴量の式（0012 の表）、
  `extract_session` / `Standardizer` の API は変えない。

## 理由

- **ファームウェアを変えない。** #7 で確かめた取りこぼし 0 の状態を崩さず、書き込み直しと確認のやり直しを避ける。
- **ずれが小さい。** 64 サンプル・16 kHz で 4 ms。窓 1.0 秒、検出の区間 `[t − 0.5 s, t + 1.5 s]`（`docs/evaluation.md`）に
  対して小さい。
- **#12 の記録を始める前に意味を固定する。** M1 のデータの `t_ms` の意味が、記録の途中で変わらないようにする。

## 根拠（コードとボードコア）

- `firmware/logger/logger.ino` の `on_pdm()` は、`PDM.read()` でチャンクを読み終えた**後**に `chunk_t_ms = millis()` を取る。
- ボードコア（`mbed_nano` 4.6.0 の `libraries/PDM/src/rp2040/PDM.cpp`）は、64 サンプル（16 kHz で 4 ms）のバッファが
  埋まってからコールバックを呼ぶ。実測でも `sample_index` の差分は全区間で 64、チャンク間の `t_ms` の差は 4 ms
  （docs/log/2026-09-19.md）。
- したがって `t_ms` は、チャンクの先頭ではなく終端側の時刻になる。`t_ms` が終端側の時刻だという根拠はここに置く。

## 実測

基板を叩いて、IMU の立ち上がりと音の立ち上がりの時刻の差を見る。実機、装着不要。被験者は `self`（人は写らない・話さない）。
記録は確認が済んだら `data/raw/` から消し（`docs/recording-protocol.md`）、数字だけを `docs/log/` に残す。波形は貼らない。

### 方法

- 基板を机に置き、`tools/record.py --cond quiet --duration 60` で記録しながら、約2秒おきに基板（またはすぐ横の机）を
  ペンで軽く叩く。30 回前後。
- 使い捨てのスクリプト（リポジトリに入れない）で、下の規則で抽出する。規則は記録を見る前に決め、結果を見てから変えない。

### 抽出の規則

- IMU の候補: 加速度のノルムが、直前 0.5 秒（その行を含まない）の中央値から、同じ区間の中央絶対偏差の 8 倍
  （下限 0.01 g）を超えて外れた行。候補の後 0.8 秒は次の候補を取らない（叩きの最低間隔。余韻を数えない）。
  その行の `t_ms` を IMU の立ち上がりとする。
- 音の候補: IMU の立ち上がりの前後 100 ms の範囲で、`|x|` が、IMU の立ち上がりの 0.6〜0.1 秒前の区間の RMS の 8 倍を
  超えた最初のサンプル。範囲の中に複数あっても、最初の1つだけを使う。時刻は、チャンクの `t_ms` を (a) 先頭サンプルの
  時刻とみなした場合と、(b) チャンクの終端側の時刻とみなした場合（先頭 = `t_ms` − チャンクのサンプル数 ÷ 16000）の両方で出す。
- 対応: IMU の候補1つに音の候補が1つ見つかったものだけを対にする。音が見つからない IMU の候補は除外して数える。
  記録の最初と最後の 1 秒にある候補も除外する。
- 出すのは、差 Δ = 音 − IMU の (a) と (b) それぞれの中央値・四分位範囲・最小・最大、対にできた数、除外した数（理由別）。
  対にできた数が 15 未満なら、規則は変えずに録り直す。

### この実測で言えることの限界

- IMU は約 9.5 ms 周期で、立ち上がりは「次に読まれた行」の時刻にしか現れない（平均で約 +4.7 ms、最大で約 +9.5 ms
  遅れて見える）。IMU 内部のフィルタと PDM の間引きフィルタにも数 ms の遅れがある。
- 4 ms の差を、叩きの実測だけで切り分ける分解能は無い。実測は「ずれの大きさが ±10 ms 程度に収まっているか」の確認。
- (a) と (b) のどちらが正しいかを、この実測の数字で決めることはしない。決めているのは上の「根拠」。

### 結果

60 秒の記録1回（2026-09-20）。取りこぼしは IMU・音声とも 0 箇所。叩きは約 1.2 秒おきで、約2秒おきの予定より多い 50 回に
なった（候補の後 0.8 秒の不応期より間隔は長い）。規則は変えていない。

| 項目 | 値 |
|---|---|
| IMU の候補 | 50 |
| 対にできた数 | 50 |
| 除外（記録の最初と最後の 1 秒 / 音が見つからない） | 0 / 0 |
| Δ = 音 − IMU、(a) `t_ms` を先頭サンプルの時刻とみなした場合 | 中央値 −3.9 ms、四分位範囲 −6.0〜−1.8 ms、最小 −99.9 ms、最大 +0.9 ms |
| Δ = 音 − IMU、(b) `t_ms` を終端側の時刻とみなした場合（採用した読み方） | 中央値 −7.9 ms、四分位範囲 −10.0〜−5.8 ms、最小 −103.9 ms、最大 −3.1 ms |

- (b) は (a) よりちょうど 4 ms 小さい（全チャンクが 64 サンプルだったため）。
- どちらの読み方でも、中央値と四分位範囲は ±10 ms 程度に収まった。音が IMU より先に見えるのは、IMU の立ち上がりが
  「次に読まれた行」にしか現れないことと合う向き。上の「限界」のとおり、この数字から (a) と (b) のどちらが正しいかは言えない。
- 50 対のうち 2 対は外れている（(a) で −24.9 ms と −99.9 ms）。−99.9 ms は音を探す範囲の左端で、叩きより前の音が閾値を
  超えたものと見られる（未確認）。規則どおり除外せずに数え、中央値と四分位範囲で読む。

## 影響する場所

- `docs/data-schema.md`: `audio.wav` の節の一文。
- `analysis/features.py`: 上の「読む側の計算」。`analysis/test_features.py` の合成セッションは、チャンクの `t_ms` を
  「先頭サンプルの時刻 + チャンクの長さぶん」で作る。取りこぼし（チャンク 25 個）のテストの無効な窓は 5 つから 4 つになる
  （飛びの区間が `(3.996, 4.100)` から `(4.000, 4.100)` になり、窓 `[3, 4)` が外れる）。
- `docs/decisions/0012`: 音声サンプルの時刻と音声の飛びの判定の段落を、この記録で置き換えた。特徴量の表は変えていない。
- `docs/decisions/0006`: 「#15 で扱う」とした箇所に、この記録への参照を足した。
- `analysis/evaluate.py` は変えない。`session_span` はチャンクの `t_ms` をそのまま記録の範囲に使う。4 ms の差は、
  60 秒の記録の長さの 0.01% 未満。
- `tools/record.py`、`tools/check_session.py` は変えない。`check_session.py` は生の `t_ms` の差分で取りこぼしを見る。
  チャンク長が一定なら `features.py` の判定と一致する。

## 塞がっていない点

- `loop()` が `pdm_buf` と `chunk_t_ms` を送っている間に次のコールバックが来ると、送信中のバッファと時刻が上書きされうる
  （コード上の競合。docs/log/2026-09-19.md、#7 の log は docs/log/2026-09-20.md）。
- #7 の取りこぼし 0 は `t_ms` の飛びが無いことを示すだけで、中身の上書きが無いことまでは示さない。
- この記録は「競合が起きても、`t_ms` が常にそのチャンクの時刻になる」とは主張しない。ファームウェアを変えない決定は
  そのままにする。
