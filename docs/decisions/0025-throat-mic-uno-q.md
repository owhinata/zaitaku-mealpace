# 0025 音のチャンネルを咽喉マイク SH-12JK に替え、基板を手元の UNO Q にする

`docs/evaluation.md`・`docs/data-schema.md`・`analysis/`・`tools/`・`firmware/` は変えていない。CLAUDE.md の「実装方針」「データの扱い」の該当行は人が差し替える

## 決定

### センサ

- 音のチャンネルを咽喉マイク 南豆無線 SH-12JK（エレクトレット、3.5 mm 3 極）にする。発注済み（10/2、即納）。
- M1・M2 の第一候補（Nano RP2040 Connect 基板の LSM6DSOX と PDM マイク MP34DT06JTR、docs/decisions/0002）は、M3 以降の構成では使わない。
  IMU は 0026 の条件で外付けを足す。

### 基板

- 手元の Arduino UNO Q を使う。4GB 版を検出器、2GB 版をベンチと予備にする。
- 「UNO Q は応募時点では使わない」というこれまでの前提（`docs/proposal.md` 7 章）を取り消す。

### 構成

```
 [咽喉マイク SH-12JK]（喉元。エレクトレット）
        │ 3.5 mm 3 極
 [USB オーディオアダプタ]
        │ USB
 [USB-C ハブ（PD パススルー）] ◀── [PD 対応モバイルバッテリー]
        │ USB-C
 [UNO Q]
   ├─ Linux 側: ALSA → メモリ上のバッファ → 窓ごとの特徴量 → 推論 → 波形は破棄
   │             （ディスクに音声を書かない。WAV・raw とも）
   │        ▲▼ RPC（表示の状態を渡す。音声は渡さない）
   └─ MCU 側: LED（表示。docs/decisions/0018 の規則）
```

- Linux 側: ALSA から音声をメモリに取り、`docs/evaluation.md` の窓（1.0 秒 / ホップ 0.25 秒）ごとに特徴量に変換して破棄する。ディスクに WAV を書かない。
- MCU 側: LED。Linux 側と RPC で結合する。
- 電源は PD 対応モバイルバッテリー。

### データの扱い（検出器）

- 検出器の Linux 側は音声をディスクに書かない（WAV・raw とも）。メモリ上で特徴量に変換して破棄する。ログ、標準出力、ネットワーク、MCU への RPC にも
  音声の波形を出さない。docs/decisions/0005 の「検出器ファームウェアは生の音声波形を保存も送信もしない」を、UNO Q の構成では Linux 側のプログラムと
  MCU 側のスケッチの両方に当てる。
- 学習用の `self` の生の音声（開発用の計測。0005 の記録ファームウェアに当たるもの）は、USB オーディオアダプタを PC に挿して PC で録り、`data/raw/` に置く
  （`self` のみ。CLAUDE.md「データの扱い」の `self` の規則）。UNO Q の検出器のプログラムには録音の機能を持たせない。UNO Q を通した生の音声の記録が要る
  ことになったら、検出器とは別のプログラムとして、先に `docs/decisions/` に記録する。
- 検出器が窓ごとの特徴量と検出の結果を PC に送る経路と形式（0021 の DETECT / FEAT に当たるもの）は、M3・M4 の Issue で決め、`docs/data-schema.md` を直す
  plan で Codex のレビューを通す。特徴量は生の波形ではないので 0005 の範囲内（`self` のみ。`p1` は本人試用の前に別に決める）。
- `docs/data-schema.md` は、時刻の基準を装置の `millis()` とし（「共通」の節）、音声を基板の PDM マイクから装置経由で受ける前提で書かれている。この記録だけでは
  M3・M4 の数字は出せない。後の plan（M3 の Issue。`docs/data-schema.md`・`tools/`・`analysis/` を同時に直す）で、少なくとも次を決める。
  1. PC で録る咽喉マイクの音声と、マーカー（`events.csv`）の時刻の合わせ方（共通の時計を何にするか）。
  2. 音声の形式（サンプリング周波数、ビット深度、チャンネル数、ファイル名）と `meta.json` の `sensors`・`sample_rates`。
  3. UNO Q の検出器が PC に送る DETECT / FEAT に当たるものと META（0021 の形式をそのまま使うか、変えるか）。
  4. 既存の評価器（`analysis/split.py`、`analysis/evaluate.py`、`analysis/evaluate_detector.py`）との接続（読めるファイルの形にするか、読み口を足すか）。

## 理由（人）

- UNO Q は手元にある。
- 咽喉マイクの入力が、USB オーディオアダプタで電子工作なしに取れる見込み（バイアスと ALSA での取り込みは未確認。M3 で確かめる。下の「確かめていないこと」）。
- 装置と PC の推論コードが同じ Python になる。

## 選ばなかった案

- **UNO Q＋UNO Media Carrier（3.5 mm のマイク・ヘッドホン兼用ジャック）、UNO Q＋UNO Breakout Carrier（MIC IN がピン。ジャックとバイアスは自作）。**
  兼用ジャックに 3 極のマイクを挿せるか、バイアスが出るかが未確認。USB オーディオアダプタなら電子工作が要らない。
- **今の Nano RP2040 Connect＋プリアンプ→ADC。** #35 と同じ道で、ハムと ADC の取りこぼしが課題。
- **圧電の再試行を先にする。** #35 の構成では信号が見えず、配線の改良からになる。
- **#28 の判定を待ってから決める。** 次の手に移るのが遅れる（0024）。

## 確かめていないこと

- SH-12JK で嚥下の信号が見えるか（M3 の (1)）。
- USB オーディオアダプタがマイクのバイアス（プラグインパワー）を出すか。UNO Q の ALSA で取れるか。取れるサンプリング周波数。
- PD パススルーのハブ経由で UNO Q とアダプタが給電されたまま動くか。モバイルバッテリーの持ち時間。電源由来の雑音。
- arduino-cli で UNO Q の MCU 側のビルドと書き込みができるか（0001 の A 案）。
- Linux 側の 1 ホップ（0.25 秒）の処理時間、RPC の遅れ。
- LED をどこに出すか（UNO Q の基板の LED か、#32 の表示器か）。0018 の規則（緑・黄の「目安」、更新が 1.0 秒無ければ消灯）をそのまま当てられるか。

### 検出器の境界

1. 装置（食卓で使う形態）は、咽喉マイク、マイクから UNO Q への入力のリンク、UNO Q（Linux 側・MCU 側）、LED までを指す。
2. マイクから UNO Q への入力のリンクは、有線（3.5 mm のケーブルと USB オーディオアダプタ）でも無線（送信機から UNO Q の Bluetooth の A2DP シンクへ）でも、
   装置の内側のセンサ入力として扱う。マイクの音がこのリンクを通ることは、検出器が生の音声波形を「送信する」ことに当たらない。無線の入力は USB オーディオの入力と同じに扱う。
3. 「検出器は生の音声波形を保存も送信もしない」（CLAUDE.md「データの扱い」、0005、上の「データの扱い（検出器）」）は、検出器のプログラム（UNO Q の Linux 側のプログラム・
   MCU 側のスケッチ）が入力を受け取った後の扱いの決まりで、変えない。Linux 側は受けた音声をメモリ上で特徴量に変換して破棄し、ディスク（WAV・raw・一時ファイルとも）、
   ログ、標準出力、ネットワーク、MCU への RPC に波形を出さない。無線で受けた入力にも同じに当てる。
4. 入力を受けた後に、検出器のプログラムの外の仕組みが波形を別の出口へ流すことも、送信（または保存）に当たるものとして扱う。例: PipeWire / WirePlumber が入力のノードを
   再生の出力（USB オーディオアダプタのヘッドホン出力など）、別のユーザーのセッション、ネットワークのモジュールにつなぐこと。構成 B の試しでは、既定の自動リンクで
   アダプタの再生側へつながり、設定の前はログイン画面（lightdm）側の PipeWire が音を受けていた（docs/log/2026-10-08.md、0030「UNO Q に残した設定」）。
5. 無線のとき、送信機が音を送ってよい相手は、その家庭の装置の UNO Q だけ（ペアリング済みの 1 台）。送信機が他の機器（スマートフォン、他の Bluetooth の受信機など）と
   つながりうる状態は、装置の外への出力として扱う。
6. 学習用の記録の経路（0028・0030。生の音声を ssh で PC に流し、PC が `data/raw/` に書く）は、検出器ではなく記録専用の経路のまま（0005 の記録ファームウェアと
   同じ扱い。`self` のみ）。この境界は記録の経路を広げない。同じ UNO Q で検出器と記録を同時に動かさない（0028 決定 3）も変えない。

### この境界で認めること・認めないこと

- 認める: 検出器の入力を無線の送信機にすること自体を、「検出器は送信しない」の違反としない（下の「無線を採る前の条件」を満たしたうえで）。
- 認めない（今までどおり）: 検出器の Linux 側が音声をディスク・ログ・標準出力・ネットワーク・RPC に出すこと。UNO Q から外へ音声を出すこと（Bluetooth・Wi-Fi・有線の
  ネットワーク・再生の出力）。PC へ生の音声を送る機能を検出器に持たせること。`p1` の生の音声の記録の経路を、この追記で決めること（本人試用の前に別に決める。0024、0028 決定 4）。
- 今は採っていない: 検出器（M4）の入力は有線。無線の入力を検出器で採るときは、次の条件を満たす送信機と設定を `docs/decisions/` に新しく記録し、Codex の plan レビューを
  通し、CLAUDE.md の該当行（「UNO Q の Linux 側は ALSA からメモリに取り」。A2DP の入力は PipeWire から取る）を人が直してから実装する。それまでは、検出器のプログラムが
  無線の入力を読む plan は、CLAUDE.md の今の文言のとおりに扱う。

### 無線を採る前の条件（採るときの記録で満たす）

- 入力が小さいときに無音に置き換えない送信機（ゲートが無いか、切れる）。`quiet` の基準を、有線と同じ規則（10/7 に固定した規則）で確かめる。
- 送信機は家庭内で UNO Q とだけペアリングする。初回のペアリングは UNO Q を先に起動して行う。ペアリングの後は、UNO Q の Discoverable・Pairable を切る。
- 送信機の接続先を UNO Q に固定する方法と、UNO Q が無い・切断した・再起動したときにも送信機が他の機器へ音声を送らないことの確かめ方（上の境界 5）。
  今の送信機は電源を入れるたびに新規ペアリングで来る（0030「UNO Q に残した設定」）。確かめられるまでは採らない。
- 入力のノードを、検出器のプログラムの外の出口（再生の出力、別のユーザーのセッション、ネットワーク）へつながない設定と、その確かめ方（上の境界 4）。
- ProtoPedia の記事に、マイクと UNO Q の間が無線であることと、届く範囲（使う送信機の仕様の値）を書く。
- 遅延（構成 B では叩きの `Δ` が +31〜+168 ms）が、LED の目安の表示（docs/decisions/0018 の規則）とイベントの数え方に与える影響を確かめる。

### 根拠（人の考え、10/3）

- 決まりの意図は、食卓の会話を録音・保存せず、音声を装置の外へ出さないこと（`docs/proposal.md` 5 章「処理は装置内で完結し、音声も映像も外に出さない」
  「食卓の会話を録音・保存しない」）。マイクから基板への無線のリンクは装置への入力で、有線のケーブルを置き換えたもの。
- ただし電波は家の外へ届きうる。送信機は起動後に近くの接続できる機器を探す（10/8 は UNO Q の Class of Device を Audio/Video に変えるまで UNO Q を相手にしなかった）。
  そのため、境界 4・5 と「無線を採る前の条件」を文章にした。

### 確かめていないこと

- 無線のリンクの暗号化の有無。構成 B のペアリングは Secure Simple Pairing（入出力の無い承認、Just Works）で行ったが、リンクが暗号化されていたかは確かめていない。
  Just Works は中間者への耐性が無い。
- ペアリングの相手を取り違えたとき（近くに別の A2DP の受け手がある、別の UNO Q がある）の送信機の挙動。`JustWorksRepairing = always` の下で、同じアドレスを名乗る
  機器の再ペアリングを UNO Q が受けるか。
- 製品ページ・取扱説明書の電波に関する注意書きの中身（10/10 に人が取扱説明書の 5・6 を読み、ゲートの記述が無いことだけを確かめた）。
- 家の外へ届く距離（取扱説明書の通信距離 約 20 m は見通しの値）。
- ゲートの無い送信機の候補と、その遅延・コーデック。
- NZ-W210C のノイズゲートが嚥下の信号に与える影響（静かな区間が無音に置き換わることだけを確かめた）。
- メーカー（南豆無線）が公開している使用例（咽喉マイクを食事中に着けて嚥下音を確かめた例、言語聴覚士が嚥下音と咽頭の残留音を聞いた例）の出どころ（人の考え 10/3 の材料。出どころを確かめていない）。
