## 0017「M2 への課題」への答え

1. **日をまたいでも崩れないこと**: 学習に使っていない 3 日の日ごとの数字は、検出率 0.200 / 0.082 / 0.174、誤検出率 2.38 / 0.35 / 2.89 回/分。
   1 日 1 本で会話の有無も日で違うので、日の差・食事の差・装着の差は分けられない。「崩れない」の結論は出せない。誤検出率は日で約 8 倍の幅がある。
2. **咳のときの誤検出を減らすこと**: `c` に紐づく誤検出の塊 2 / 誤検出の塊 89。`meal` の `c` は 3 回で、割合の比較には少ない。誤検出のほとんどは咳の直後ではない。
   M1 の評価側（咳のマーカーの 48% に誤検出。条件とモデルが違う）との直接の比較はできない。
3. **IMU と音の結合の方式を決めること**: 0019 で決めた（装置で計算した窓ごとの特徴量ベクトルを EI の分類器に入れる）。#27 の数字はその方式の装置上の数字。
   片方だけの比較は出していない。

## 原因の切り分けの材料（結論は書かない。読みは推測）

- 装置と PC の採点は一致するので、届かない原因は装置の推論の実装の側ではなく、特徴量の分布か閾値の位置の側にあるように見える（推測）。
- 会話あり 0.200 / 2.38 回/分、会話なし 0.126 / 1.79 回/分。誤検出率は両方で合格線を超える。会話の音だけでなく、咀嚼・食器・首の動きなど非嚥下区間の中身の側も効いているように見える（推測）。
- 常時陽性の場合は検出率 1.000・誤検出率 0.07 回/分で、陽性窓の割合は 0.018（#22 の収集日4 は 0.012）。陽性の量は大きく変わらず、陽性が嚥下の区間の外に出ている（推測）。
- #22 の収集日4 の参考値（58.8% / 0.75 回/分。M1 の手順、すべての嚥下に `s`）とは条件も `s` の決まりも違う。参考値であり M2 の数字ではない。
- 評価側の `meal` で閾値の走査はしていない（0021）。

2. **[high] 検出器の取り込み面（16 kHz、2 面 × 4000 サンプル、最長 0.5 秒）が、特徴量化の後に消されず、次のスライスで上書きされるまで RAM に残る**（`firmware/detector/audio_capture.cpp` の
   `audio_capture_release`。ギャップ時の破棄と初期化も同じ）。事実として正しい。人の判断で **CONCERN**。理由:
   - 不変条件 4（AGENTS.md）が違反と定める経路は「ファイル、ログ、シリアル出力、デバッグ用ダンプ」で、RAM 上の上書き待ちは入っていない。0005 の趣旨は外に出さないこと。
   - 外に出る経路は `firmware/detector/` に無い（シリアル送信は META・DETECT・FEAT のフレームと計測の数字だけ。`WiFi.begin()` は呼ばず BLE も使わない。ファイルも書かない）。

   - **解釈をここに残す**: 「特徴量に変換した後に破棄する」は、波形を保存・送信せず、処理に要る最小の RAM 上のバッファが次のデータで上書きされることを含む。外に出る経路が無いことが条件。
   - Nano の検出器は直さない（M3 で UNO Q に移る。0025）。UNO Q の Linux 側でも同じ解釈を使う（メモリ上のバッファは可、ディスク・ログ・RPC・ネットワークに出さない）。
