# 0011 `docs/evaluation.md` が決めていない点の解釈を固定する

日付: 2026-09-20　状態: 採用

`docs/evaluation.md` の定義と合格線は変えていない。定義が決めていない点の読み方をここに固定し、
`analysis/evaluate.py` と `analysis/split.py` を定義に合わせて直した（#10）。解釈は人が決めた。
採否の経緯は Issue #10 のコメントにある。

## 決定

- 陽性窓 `[w, w + 1.0]` が嚥下の区間に「ある」とは、窓の中心 `w + 0.5` が閉区間 `[t − 0.5, t + 1.5]` に
  入ること（`t − 1.0 ≤ w ≤ t + 1.0`）。検出と、非嚥下区間の陽性（誤検出）の判定に、同じ述語を使う。
  どの嚥下の区間にも中心が入らない陽性窓が「非嚥下区間で陽性になった」窓。
- 誤検出の回数は、先に陽性窓を連続の塊（間隔が `HOP_S * 1.5` 以下）にまとめてから数える。塊の中に、
  どの嚥下の区間にも中心が入らない窓が1つでもあれば、その塊で誤検出1回。全部の窓が嚥下の区間に入る塊は
  0 回。嚥下の区間をまたぐ連続も1つの塊で、1回（「陽性が連続する窓は 1 回と数える」の文言どおり）。
- 1つの陽性窓が、近接した2つの嚥下を両方検出してよい（定義の文言どおり）。
- 嚥下が0件のセッションの検出率は `None`（未定義）。誤検出率は計算する。
- 非嚥下区間の長さ = 記録の長さ −（各嚥下の区間を記録の範囲に切り詰めて結合した和集合の長さ）。
  非嚥下区間が 0 以下なら誤検出率は `None`。
- 記録の範囲は、`imu.csv` と `audio_chunks.csv` の `t_ms` を合わせた最小〜最大（閉区間）。
  `tools/record.py` のマーカーは直前に届いたフレーム（IMU とは限らない）の `t_ms` を使うので、IMU だけの
  範囲にはしない。範囲の外の嚥下マーカー（フレームが届く前に打った `t_ms = 0` など）はエラーにする。
  範囲の両端ちょうどのマーカーは受け付ける。
  1つのストリームの中で `t_ms` が逆行する、または 1 秒を超えて飛ぶセッションは、範囲を出さずにエラーにする
  （外れた `t_ms` が1行あるだけで記録が長く見え、誤検出率が薄まるのを防ぐ）。
- 複数セッションの集計は回数の合算: 検出率 = Σ検出 ÷ Σ嚥下、誤検出率 = Σ誤検出の回数 ÷ Σ非嚥下区間の分数。
  評価側が3セッション未満ならエラーにする。
- 混同行列はイベント単位: TP = 検出された嚥下、FN = 検出されなかった嚥下、FP = 誤検出の回数。TN は
  イベント単位では定義できないので出さない（`None`）。
- `analysis/split.py` は `--eval-min` が 3 未満、`subject` が `self` / `p1` 以外なら止まる。フォルダ名は
  `YYYYMMDD-HHMMSS_<subject>_<cond>`（`docs/data-schema.md` の列挙）に完全一致で照合し、形式に合わない
  ディレクトリ、`meta.json` が無い・オブジェクトでない・`subject` が `self` / `p1` でない・フォルダ名の
  subject と違うセッションがあれば止まる（通常ファイルは無視）。名前順に並べて後ろから `eval_min` 個を
  評価側にする動作は変えない。窓単位の分割は足さない。セッションのフォルダがシンボリックリンクなら止まる
  （同じセッションを別名のリンクで並べて、学習側と評価側に同じ実体を入れさせない）。`data/raw` 自体のリンク
  （docs/decisions/0007）は対象にしない。
- 上の数え方は `analysis/test_evaluate.py`・`analysis/test_split.py` の合成データで固定する。

## 理由

直す前の実装には、定義との食い違いがあった。

- E1: 区間に入るかの判定が、検出側（窓の開始か終端が区間内）と誤検出側（開始だけ）で違い、同じ陽性窓が
  検出と誤検出の両方に数えられた（嚥下 10.0、陽性窓 9.0）。
- E2: 定義は閉区間だが、実装は上端だけ開いていた。
- E3: 嚥下時間を `件数 × 2.0` で引き、区間が重なると二重に引いた（嚥下 10.0 と 11.0 で 4.0 秒。和集合は 3.0 秒）。
- E4: 記録の端で区間を切り詰めなかった。`events.csv` の `t_ms` は装置の `millis()` で 0 始まりではないのに、
  記録の開始時刻を受け取る引数が無かった。
- E5: 非嚥下時間が 0 以下のとき `1e-9` に丸め、巨大な誤検出率を返した。
- E6: 複数セッションを集計する入口が無く、評価側が3セッション未満でも止まらなかった。
- E7: 陽性の連続を嚥下の区間で切り、区間をまたぐ1つの連続を2回と数えた。
- S1: `split.py` が `--eval-min` に 3 未満を許した。`0` だと全セッションが評価側になった。
- S2: subject の判定が部分文字列 `_{subject}_` の有無だけだった。手で作った
  `20260927-120000_p1_retake_self_water` は self に入った。名前の形式も `meta.json` も見ていなかった。

M1 の分岐点の数字（#13）はこの2つのスクリプトが出す。実データを見る前に数え方を固定しておけば、結果を見てから
数え方を動かす余地が残らない（0003 と同じ理由）。

## 既知の弱点

- この定義では、常に陽性を出す分類器は検出率 100%・誤検出は1セッションに1回となる（嚥下1件・60秒の例で
  1.0345 回/分、180 秒のセッションなら約 0.33 回/分）。M1 の合格線を通りうる。
- 定義と合格線は動かさない。#13 の報告に「常時陽性の場合の数字」と「陽性窓の割合」を参考値として並べ、
  #14 の判定で人が見る（人が決定）。
- この挙動はテスト（EV16）で固定してある。

## 塞がっていない経路

- `aggregate` は、渡された辞書の件数しか見ない。呼び出し側がわざと、同じセッションを別名で3つ渡す、窓ごとに分けた
  結果を渡す、`p1` の結果を渡す、と書けば通る。入力ミスでは通らない。実装後のレビュー（#10 のコメント）の指摘で、
  人の判断で CONCERN とした。#13 で、`split_sessions` の `eval` の一覧からセッションごとに `event_metrics` を作って
  `aggregate` に渡す経路を1本にし、#14 の関門のレビューで見る。
